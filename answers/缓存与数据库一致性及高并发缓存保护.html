1. 缓存与数据库一致性策略如何取舍？

缓存与数据库一致性的核心，不是追求所有场景下的"绝对一致"，而是根据业务对 一致性、性能、复杂度 的要求做取舍。

最常见、也是业务系统里比较推荐的方案是：

Cache Aside（旁路缓存） + 更新数据库后删除缓存

2. Cache Aside 读流程

text
请求
 ↓
查 Redis
 ↓ 命中
直接返回

 ↓ 未命中
查 DB
 ↓
写 Redis
 ↓
返回

基本逻辑：

  1. 请求先查询 Redis。
  2. Redis 命中，直接返回。
  3. Redis 未命中，查询数据库。
  4. 将数据库查询结果写入 Redis。
  5. 返回数据。

这种模式下：

数据库是事实源（Source of Truth），Redis 是性能加速层。

缓存即使出现问题，也可以删除并重新从数据库构建。

3. 写数据为什么推荐"更新 DB → 删除缓存"？

推荐：

text
更新 DB
  ↓
删除 Redis

而不是：

text
更新 DB
  ↓
更新 Redis

原因是直接更新缓存，在高并发情况下容易发生写入顺序错乱。

例如两个并发请求：

text
请求 A：DB 写成 10
请求 B：DB 写成 20

请求 B 先更新缓存 = 20
请求 A 后更新缓存 = 10

最终可能变成：

text
DB = 20
Cache = 10

数据库已经是最新值 20，但是缓存却被旧请求覆盖成 10。

因此更常见的策略是：

text
更新数据库
↓
删除缓存
↓
下一次查询缓存 miss
↓
重新查询 DB
↓
重新构建缓存

这样缓存只负责失效，而不是主动维护复杂的并发更新顺序。

4. "更新 DB → 删除缓存"是不是绝对一致？

不是。

Cache Aside 本质上通常提供的是 最终一致性。

仍然存在一个经典并发问题。

例如：

text
线程 A：
1. 查缓存，没有
2. 查 DB，读到旧值 10

线程 B：
3. 更新 DB = 20
4. 删除缓存

线程 A：
5. 把刚才读到的旧值 10 写入缓存

最终：

text
DB = 20
Cache = 10

因此：

删除缓存并不意味着理论上的强一致，只是大幅降低了缓存与数据库不一致的复杂度。

5. 如何进一步降低不一致概率？

工程上常见组合：

text
Cache Aside
+
TTL
+
删除失败重试 / MQ 补偿
+
必要时延迟双删

5.1 TTL

给缓存设置合理的过期时间。

即使因为极端并发产生了脏缓存：

text
DB = 新值
Redis = 旧值

缓存最终也会自动过期，然后重新从 DB 构建。

TTL 相当于最终一致性的兜底机制之一。

5.2 删除失败重试 / MQ 补偿

例如：

text
更新 DB 成功
↓
删除 Redis
↓
删除失败
↓
发送 MQ / 写入重试队列
↓
后台重新删除 Redis

这样可以避免：

text
数据库已经更新
但缓存删除失败
↓
旧缓存一直存在

对于比较重要的数据，这是比单纯"删一次缓存"更可靠的方式。

5.3 延迟双删

例如：

text
更新 DB
 ↓
删除 Redis
 ↓
等待一小段时间
 ↓
再次删除 Redis

目的就是处理前面提到的并发场景：

text
A 查询到旧 DB
↓
B 更新 DB
↓
B 删除缓存
↓
A 又把旧数据写回缓存

第二次删除尝试把 A 回填的旧缓存再次删除。

但是延迟双删并不是所有业务都应该默认使用，因为：

  • 增加系统复杂度。
  • 延迟时间很难精确确定。
  • 仍然不是严格意义上的强一致。

因此通常根据业务一致性要求决定是否采用。

6. 哪些场景使用什么一致性策略？

场景推荐策略
商品详情、配置、普通业务数据Cache Aside + DB 更新后删缓存 + TTL
高并发读、低频写Cache Aside
缓存删除偶尔失败MQ / 重试队列补偿删除
可以容忍几秒旧数据TTL + 最终一致性
余额、库存扣减、支付状态不依赖普通缓存保证一致性
极高一致性要求DB 事务 / 原子操作 / 必要的分布式事务

7. 为什么缓存不应该轻易作为事实源？

例如：

text
Redis: 余额 = 100
DB:    余额 = 80

此时到底相信谁？

一般设计应该是：

text
DB = 事实源
Redis = 性能层

缓存错了：

text
删除缓存
↓
重新读取 DB
↓
重建缓存

因此普通业务缓存应该尽量做到：

缓存可以丢，数据库不能错。

8. 强一致业务为什么不能单纯依赖缓存？

例如库存：

text
库存剩余：1

用户 A → 下单
用户 B → 同时下单

这时候真正的问题已经不是：

Redis 和数据库缓存是否一致？

而是：

两个并发请求如何保证只有一个请求成功扣减库存？

因此核心应该转向：

  • 数据库事务
  • 乐观锁 / 悲观锁
  • CAS
  • Redis 原子操作
  • Lua Script
  • 库存预扣
  • 消息队列
  • 分布式事务

也就是说：

缓存一致性解决的是"读到什么数据"的问题，而库存并发控制解决的是"业务状态能不能被正确修改"的问题。

两者不能混为一谈。

9. 缓存击穿：大量并发同时 Cache Miss 怎么办？

假设某一个热点 Key：

text
product:123

平时：

text
10 万 QPS
↓
Redis
↓
DB 几乎没有压力

突然缓存失效：

text
product:123 过期

这时候 10 万个请求同时：

text
Redis MISS
↓
全部查询 DB

数据库可能瞬间被打垮。

这就是典型的：

缓存击穿（Cache Breakdown / Hot Key Expiration）

10. 方案一：互斥锁

核心思想：

缓存失效之后，只允许一个请求查询数据库。

流程：

text
大量请求
   ↓
查 Redis
   ↓ MISS
抢分布式锁
   ↓
┌────────────────┐
│ 抢到锁的请求    │
│ 查询 DB         │
│ 写 Redis        │
│ 释放锁          │
└────────────────┘

其他请求
↓
没有抢到锁
↓
等待 / 重试
↓
重新读取 Redis

Redis 中可以使用类似：

text
SET lock:product:123 1 NX EX 5

含义：

  • NX：Key 不存在时才写入。
  • EX 5：锁 5 秒后自动过期。
  • 防止服务异常导致死锁。

11. 为什么抢到锁之后还要再查一次缓存？

这是一个非常重要的细节。

例如：

text
A 查 Redis → MISS
B 查 Redis → MISS

A 抢到锁
A 查询 DB
A 写 Redis
A 释放锁

B 此时才抢到锁

如果 B 抢到锁之后直接：

text
查询 DB

实际上这次数据库查询完全没有必要。

因为 A 已经：

text
DB → Redis

完成了缓存回填。

所以正确流程应该是：

text
查缓存
↓
MISS
↓
抢锁
↓
再次查缓存
↓
仍然 MISS
↓
查询 DB

这就是：

Double Check（双重检查）

12. 方案二：Singleflight / 请求合并

如果大量请求同时查询：

text
product:123

其实没有必要产生：

text
1000 个请求
=
1000 次 DB 查询

可以让：

text
第一个请求
↓
真正查询 DB

其他 999 个请求
↓
等待第一个请求的查询结果

最终：

text
1000 个请求
↓
1 次 DB 查询

这就是：

Singleflight / Request Coalescing（请求合并）

Node.js 中可以维护一个正在执行的 Promise：

js
const pending = new Map();

async function getProduct(id) {
  const key = `product:${id}`;

  const cached = await redis.get(key);

  if (cached) {
    return JSON.parse(cached);
  }

  if (pending.has(key)) {
    return pending.get(key);
  }

  const task = (async () => {
    try {
      const data = await db.getProduct(id);

      await redis.set(
        key,
        JSON.stringify(data),
        { EX: 60 }
      );

      return data;
    } finally {
      pending.delete(key);
    }
  })();

  pending.set(key, task);

  return task;
}

效果：

text
请求 A ────────────────┐
请求 B ────────────────┤
请求 C ────────────────┤
请求 D ────────────────┤
                       ↓
                同一个 Promise
                       ↓
                    查询 DB
                       ↓
                  返回所有请求

13. Singleflight 的局限

假设系统部署：

text
20 个 Node.js 实例

每个实例内部都有自己的：

text
pending Map

那么：

text
实例 1 → 1 次 DB
实例 2 → 1 次 DB
实例 3 → 1 次 DB
...
实例 20 → 1 次 DB

最终仍然可能产生：

text
20 次 DB 查询

因此：

单机请求合并

text
本地 Singleflight

解决：

text
同一个服务实例内部的并发

分布式请求合并

可以进一步使用：

text
本地 Singleflight
+
Redis 分布式锁

这样能够进一步控制多个服务实例同时访问数据库。

14. 方案三：逻辑过期

对于超级热点 Key，可以不让 Redis Key 真正消失。

例如 Redis 保存：

json
{
  "data": {
    "name": "商品 A"
  },
  "expireTime": 1780000000
}

Redis Key 本身：

text
不设置物理 TTL

或者设置一个非常长的 TTL。

业务代码自己判断：

text
expireTime

如果没有过期：

text
直接返回数据

如果已经逻辑过期：

text
仍然返回旧数据
+
后台异步刷新缓存

流程：

text
请求
 ↓
读取 Redis
 ↓
发现逻辑过期
 ↓
仍然返回旧数据
 ↓
尝试抢刷新锁
 ↓
一个线程查询 DB
 ↓
更新 Redis

这样就不会出现：

text
缓存突然消失
↓
所有请求直接访问 DB

15. 逻辑过期的本质：用一致性换可用性

逻辑过期意味着：

text
缓存已经过期
↓
用户仍然可能看到旧数据

例如：

text
DB：

商品价格 = 100

Redis：

商品价格 = 90

缓存正在异步刷新期间，部分用户可能仍然看到 90。

因此它适合：

  • 首页数据
  • 热门商品
  • 排行榜
  • 活动配置
  • 热点内容
  • 推荐内容

不适合直接用于要求强一致的：

  • 账户余额
  • 最终支付金额
  • 精确库存状态
  • 强一致业务状态

16. 方案四：提前刷新缓存

假设：

text
TTL = 10 分钟

不要等到：

text
10:00:00

Key 真正消失之后再重建。

可以在：

text
TTL 剩余 60 秒

时由后台任务提前刷新。

例如：

text
09:59:00
↓
后台刷新缓存

10:00:00
↓
新的缓存已经存在

这样避免：

text
热点 Key 突然失效
↓
大量请求 Cache Miss

特别适合：

  • 可以预测的热点。
  • 首页。
  • 大促商品。
  • 活动配置。
  • 热门榜单。

17. 方案五：限流、降级、熔断

即使缓存保护措施全部失效，也不能让无限流量直接进入数据库。

例如数据库最大安全能力：

text
500 QPS

如果突然出现：

text
50,000 QPS

系统入口应该有限流能力：

text
请求
 ↓
限流
 ↓
缓存
 ↓
DB

超过系统承载能力，可以：

返回系统繁忙

json
{
  "message": "系统繁忙，请稍后重试"
}

返回旧缓存

text
Redis 数据虽然已经逻辑过期
↓
但是 DB 压力过大
↓
继续返回旧数据

服务降级

例如首页推荐：

text
正常：
个性化推荐

降级：
热门商品列表

核心思想：

数据库应该是最后一道防线，而不是缓存一失效，所有流量都直接进入数据库。

19. 缓存穿透、缓存击穿、缓存雪崩的区别

这三个概念经常一起出现。

19.1 缓存穿透

含义：

查询一个根本不存在的数据。

例如：

text
GET /product/999999999

Redis：

text
没有

DB：

text
也没有

每一次请求都会：

text
Redis MISS
↓
DB MISS

攻击者甚至可以不断生成随机 ID：

text
product:123456
product:837462
product:918273
...

导致数据库压力巨大。

解决方案：

text
缓存空值
+
Bloom Filter（布隆过滤器）

19.2 缓存击穿

含义：

一个超级热点 Key 突然失效。

例如：

text
iPhone 商品详情

缓存突然过期：

text
大量请求
↓
Redis MISS
↓
DB

解决：

text
互斥锁
Singleflight
逻辑过期
提前刷新

19.3 缓存雪崩

含义：

大量缓存 Key 在同一时间失效。

例如：

text
product:1   TTL = 3600
product:2   TTL = 3600
product:3   TTL = 3600
...
product:100000 TTL = 3600

这些缓存恰好同一时间创建。

一个小时之后：

text
10 万个 Key
同时过期

大量请求：

text
Redis MISS
↓
DB

解决方案：

text
TTL 随机化
+
分批过期
+
多级缓存
+
限流
+
降级

例如不要全部：

text
TTL = 3600

而是：

text
TTL = 3600 + random(0, 300)

让缓存失效时间分散。

21. 面试回答：缓存和数据库一致性怎么保证？

可以这样回答：

我通常使用 Cache Aside Pattern。读请求先查缓存，未命中再查询数据库并回填缓存；写请求先更新数据库，再删除缓存，而不是直接更新缓存，这样可以降低并发情况下缓存更新顺序错乱导致的不一致问题。 这种方案本质上还是最终一致性，仍然存在并发读写导致旧数据重新写入缓存的问题，所以会根据业务要求增加 TTL、删除失败重试、MQ 补偿，必要时使用延迟双删。 如果是余额、库存、支付这类强一致业务，不会依赖普通缓存保证最终业务正确性，而是让数据库事务或者原子操作负责业务状态正确，缓存主要作为查询加速层。

22. 面试回答：缓存击穿怎么解决？

可以这样回答：

对热点 Key 缓存失效导致的大量并发请求，我首先会避免所有请求同时访问数据库。 常见方案是基于 Redis 分布式锁或者 Singleflight 做请求合并，只让一个请求查询数据库并回填缓存，其他请求等待之后重新读取缓存。同时抢到锁之后还要再次查询缓存，也就是 Double Check，避免其他请求已经完成缓存回填之后仍然重复查询数据库。 如果是超级热点数据，我会考虑逻辑过期，让旧缓存继续提供服务，然后只让一个线程异步刷新缓存，从根本上避免缓存失效瞬间大量流量直接进入数据库。 最后还要配合随机 TTL、提前刷新、限流和降级，避免缓存异常进一步演变成数据库雪崩。

23. 最终理解框架

缓存相关问题可以按照下面几个层次理解：

text
第一层：正常缓存

Cache Aside
DB = Source of Truth
Redis = Performance Layer


第二层：一致性

更新 DB
↓
删除缓存
↓
TTL / MQ 补偿 / 必要时延迟双删


第三层：单热点高并发

缓存击穿
↓
Singleflight
↓
分布式锁
↓
Double Check


第四层：超级热点

逻辑过期
↓
旧数据继续服务
↓
后台异步刷新


第五层：大量缓存同时失效

缓存雪崩
↓
随机 TTL
↓
分批失效
↓
多级缓存


第六层：最后防线

限流
↓
降级
↓
熔断
↓
保护 DB

判断具体方案时，优先问三个问题：

  1. 业务能不能接受短时间脏数据？
  2. 这个数据是读多写少，还是写操作也非常频繁？
  3. 缓存错误只是影响展示，还是会造成资金、库存、支付等业务损失？

这三个问题基本决定了应该采用最终一致性、逻辑过期，还是需要把一致性保证下沉到数据库事务和原子业务操作。
