一、Workspace Agent 项目总览

  1. 001用 3 分钟介绍一下你的 Workspace Agent 项目。

    Workspace Agent 是我们目前正在迭代和内测的一个桌面端研发智能体，主要想解决从产品需求到研发落地过程中上下文和流程割裂的问题，把 PRD、RFC、可执行 Plan，再到后续代码生成、执行验证串成完整的研发链路。

    这个项目经历了两个版本。V1 是基于 Codex Desktop 做的，我们通过 Workflow Skills 加脚本去编排研发流程，同时沉淀了 Repository、Workflow 和业务规则相关的 Skills。第一版主要是快速验证场景，同时把研发过程中的知识和能力沉淀下来。

    随着功能逐渐复杂，V1 开始暴露一些问题。首先执行过程主要存在于 Codex 自己的 Agent Loop 中，缺少显式 Workflow State，中间执行到了什么阶段、调用了哪些能力、为什么失败，不方便做结构化观测和后续 Eval。

    第二，Skill 对模型本质上还是一种软约束。我们可以要求模型按照 Context Retrieval、Plan、Code、Validation 的流程执行，但复杂任务下不能保证所有关键步骤稳定执行。

    另外随着条件分支、失败重试、状态共享和 Tool 数量增加，单纯通过 Skills 编排越来越复杂；同时 Generator 和 Reviewer 在同一个 Agent 里，也存在自我验证容易延续原有假设的问题。

    所以 V2 并没有推翻 V1，而是继续复用 V1 已经沉淀和验证过的 Skills，但是重新划分职责：Agent Runtime 负责 Workflow 和 State，Skills 负责业务知识和可复用能力；Agent Reasoning 负责 Plan / ReAct 和 Tool Selection，Tool Catalog / Registry 负责工具组织与按需发现，Tool Router 负责鉴权、Scope、Risk Policy 和 Audit，Tool Runtime 负责实际执行；RAG 和 Repository Context 负责给 Agent 提供业务知识和代码上下文，再通过执行验证和独立 Critic 形成结果反馈闭环。

    我主要负责 V2 整个 Agent 链路的重编排，包括把 V1 Workflow Skills 中可以复用的能力迁移到对应 Agent 和 Node，同时参与/负责 Agent Reasoning 中的 Tool Selection、Tool Router、Repository Context、执行验证这些核心能力。另外我也负责 RAG 底座建设，以及基于真实业务问题构建 Eval Dataset、收集 Bad Case，再通过评测结果反向优化检索和 Agent 链路。

    目前 V2 还在持续迭代和内部测试阶段。

    追问链：Skills 为什么不够 → Workflow 怎么设计 → Agent Reasoning 如何做 Plan / ReAct 和 Tool Selection → Tool Catalog / Registry 怎么组织工具 → Tool Router 与 Tool Runtime 怎么分工 → RAG 怎么做 → Repository Context 怎么获取 → Critic 怎么评审 → Eval 怎么评。

  2. 002Workspace Agent 解决的核心业务问题是什么？
  3. 003V1 为什么选择 Codex Desktop + Skills，而不是一开始自己做 Agent？

    V1 我们没有一开始就自己搭 Agent，主要是因为当时最重要的是先验证这件事情本身，而不是验证我们的 Agent 基础设施能力。

    所以我们先利用 Codex 已经成熟的 Coding Agent 能力，以比较低的成本把 PRD → RFC → Plan → Code 整条链路跑起来。这个阶段 Skills 很适合，因为研发 SOP、业务规则、Repository 规范都还在快速变化，我们可以低成本修改 Skill，不断验证什么样的流程是有效的。

    V1 实际上也是一个 Know-how 沉淀过程。我们先把人的研发经验和 SOP 逐渐沉淀成 Workflow Skills、Repo Skills 和业务 Skills。等这些流程经过真实使用逐渐稳定以后，再把已经验证过的 Know-how 转化成 V2 的 Agent Node、Workflow 和 Tool Capability。

  4. 004V1 的 Skills 主要沉淀了哪些能力？
  5. 005V1 在实际使用过程中暴露了什么问题？

    V1 最典型的问题是：流程虽然能跑通，但关键步骤的推进和回退主要依赖模型遵循 Workflow Skill，缺少显式的流程状态和条件控制。

    比如我们有一个把飞书原始 PRD 转成 Workspace 标准 PRD 的 Skill。它要求 Codex 先读取文档、表格和原型，保存原始 Evidence；再做需求审查和功能拆分；发现遗漏或需要人工确认时进入 Brainstorming；随后生成子模块 PRD、整体 PRD 和导航页，最后检查原始需求覆盖率、图片和 Evidence，再完成回写。流程控制、业务 Know-how 和外部执行能力都写在同一个 Skill 里。具体先做什么、何时进入下一步、检查失败后回到哪里，仍较依赖模型执行指令。

    V2 没有直接把这个 Skill 包成 PRD Agent，而是拆解已经验证过的能力：读取飞书文档、表格和原型等确定性的外部操作下沉为 Tool；原始 Evidence 整理、需求理解和功能拆分等语义工作交给 Agent/Node；Agent 产出需求是否缺失、是否需要人工确认的判断，Workflow Runtime 根据结构化结果选择分支，必要时进入 Human-in-the-loop 或 Brainstorming。

    PRD 生成后进入独立的 Critic，检查需求覆盖、Evidence、图片和规则完整性。如果检查不通过，Critic 输出结构化问题，Workflow 再返回对应节点修改，而不是让生成 PRD 的 Agent 自己决定下一步。

    所以我们不是把 Skill 改写成 Agent，而是在对 Skill 做能力解构：Know-how 继续复用，确定性操作变成 Tool，需要推理的部分交给 Agent，流程和状态流转交给 Workflow Runtime。

    延伸追问04 QUESTIONS
    01你刚才说会把一个大的 Skill 拆成多个 Agent、Node 和 Tool。那你的拆分原则是什么？为什么 Requirement Analysis 和 PRD Generation 要拆开，而不是直接让一个 PRD Agent 从头做到尾？

    我们拆 Agent 和 Node 不是为了 Multi-Agent 而拆，核心还是根据职责边界和工程上的可控性来拆。

    第一是职责单一、边界清晰。比如 Requirement Analysis 只负责把原始 Evidence 转换成结构化需求，而 PRD Generation 只负责基于确认后的需求生成 PRD，这样每个节点的输入输出都比较明确。

    第二是可观测和可定位。如果最终 PRD 出问题，我可以判断到底是原始资料解析的问题、Requirement Analysis 理解错了，还是 PRD Generation 生成错了，而不是面对一个从原始输入一直执行到最终结果的大黑盒。

    第三是局部失败和局部重试。如果只是 PRD Generation 不符合规范，我只需要重新执行这个 Node，而不需要重新读取飞书、解析原型、做需求分析。这样不仅稳定性更好，也降低 Token 和模型调用成本。

    第四是控制 Context。如果一个 Agent 从头执行到底，随着 Tool Result、中间产物、原始文档不断累积，Context 会越来越大，甚至触发上下文窗口限制；即使没有超限，也会出现 Context Dilution，当前阶段真正需要的信息被大量无关历史信息稀释。所以每个 Agent 只拿完成自己任务所需要的 Context。

    最后是降低故障半径。一个大 Agent 从头做到尾，其中一个阶段失败可能导致整个任务重新执行；拆成有明确 State 的 Workflow 后，成功的中间产物可以保留下来，从失败节点继续。

    当然我们也不会无限拆分。我的判断标准主要是：有没有独立职责、能不能形成稳定输入输出、能不能独立验证、失败后有没有局部重试价值，以及拆分带来的额外 Context 传递和模型调用成本是否值得。

    02你刚才说每个 Agent 都有明确输入输出。那在你们 Workspace Agent 里面，Agent 之间的数据到底怎么传？

    我们使用 Global State 做跨 Agent 的状态共享，但不会把 Global State 全量塞给每个 Agent，而是每个 Node 根据职责从 State 中投影出自己的 Local Context。

    每个阶段的产物先存放在本地；对应的状态和阶段信息会同步到 Global State。每个阶段还有内部的 status，用来存放过程信息和产物。

    03那如果 Requirement Analysis Agent 输出的是结构化 State，你怎么保证它输出的结构一定正确？比如你要求它输出 features、dependencies、open_questions、evidence_refs，结果模型少字段了、类型错了，甚至引用了不存在的 Evidence ID，这种情况你们怎么处理？

    Agent 输出结构化 State 后，我不会直接让下游消费，而是先经过 Validation。

    第一层是确定性的 Schema Validation，比如通过 JSON Schema、Pydantic 或脚本检查字段是否缺失、类型是否正确、枚举值是否合法、Evidence ID 是否真实存在。这些确定性问题没必要再调用 LLM。

    第二层才是Semantic Validation。比如字段结构虽然完全合法，但是 Requirement Analysis 有没有遗漏核心需求、某个功能点引用的 Evidence 是否真的支持这个结论，这类问题单纯靠规则很难判断，就可以通过小模型或者独立 Judge 来检查。

    Validation 失败以后，会把结构化错误反馈给当前 Node 做局部 Retry，而不是让整个 Workflow 从头执行。如果连续 Retry 仍然失败，再考虑升级模型或者进入人工确认。

    04OK，那现在假设 RFC Agent 执行到一半挂了，比如模型请求超时或者进程异常。这时怎么恢复？

    我们会以 Node 执行前的稳定状态作为恢复点。RFC Node 执行失败以后，先清理这个 Node 已经产生但尚未完成验证的副作用，把 Workspace 恢复到 RFC 执行之前的状态，再对 RFC Node 做局部 Retry，上游已经完成的 PRD 不需要重新执行。

    如果某个 Node 本身执行成本非常高，比如 Fullstack Agent 一次需要修改大量代码，我们会进一步考虑按照 Plan 中可独立验证的 Step 缩小执行和 Checkpoint 粒度。只有 Step 通过 Validation 后才形成新的稳定恢复点。

  2. 012为什么选择 LangGraph？
  3. 013LangGraph 和普通 Workflow / DAG 的区别是什么？

    严格说，它们不是同一维度的概念。DAG 是有向无环图，适合表达预先确定的步骤和依赖；Workflow 是流程编排的泛称，也可以包含条件分支、重试或循环。LangGraph 则是构建有状态 Agent 工作流的框架，用 State 保存执行上下文，用 Node 执行逻辑，用 Edge 根据当前 State 决定下一步，既能表达固定流程，也能表达动态分支和反馈循环。

    比如 PRD → RFC → Plan 这部分相对稳定，可以按固定 Workflow 推进；但进入代码实现后，Agent 需要根据每轮 Tool Observation 决定继续搜索、读取文件、修改代码还是运行测试。测试失败可能回到修改，Critic 未通过也可能进入修正流程。这种后续路径依赖执行结果，不适合在开始时展开成一张固定的 DAG。

    LangGraph 还提供共享 State；配合 Checkpointer，可以保存执行进度，并在需要人工介入或发生中断时恢复。核心区别是：固定 DAG 更适合已知的依赖链；LangGraph 更适合把状态驱动的动态决策和循环明确编排出来。但它不会自动保证流程正确，退出条件、错误处理以及有副作用操作的幂等性仍需要我们自己设计。

  4. 014为什么需要 Plan + ReAct，而不是直接 ReAct？

    简单任务我会直接使用 ReAct，因为执行链路短，没有必要增加 Planning 成本。

    但复杂任务如果完全依赖 ReAct，每一轮都只根据当前 Observation 决定下一步，随着执行链路变长，全局目标约束会逐渐变弱，容易出现重复探索、遗漏关键步骤或者陷入局部循环。

    所以复杂任务我会先做一次高层 Plan，把目标拆成若干可验证的 Step。每个 Step 内部再通过 ReAct 动态调用 Tool、Observe 和调整，完成当前 Step 后再进入下一步。

    但 Plan 不是固定 DAG。执行过程中如果 Observation 证明原 Plan 不成立，比如发现代码结构和预期不同、缺少依赖或者某个 Step 已经不需要了，就会触发 Re-plan，修改后续尚未执行的 Plan。

    所以整体上是：Plan 提供全局目标和阶段约束，ReAct 解决每个阶段内部的不确定性。

  13. 023一个复杂任务经过十几轮 ReAct 后，Context 里还是会积累大量旧代码、Tool Observation、Critic Feedback、Validation Result。
    你会怎么做 Context Compression / Eviction？哪些内容可以从 Context 里清掉，哪些必须继续保留？

    我不会无限保留所有历史 Tool Result。原始 Query、当前 Plan Step、关键约束和当前 Change Scope 会持续保留，因为这些决定 Agent 不能偏离什么。

    Tool Observation 会根据后续是否还需要分层处理。当前 Reasoning 直接依赖的 Evidence 可以保留原文；已经处理过但后续还可能有价值的信息压缩成结构化 Summary；已经失效或者可以通过 Tool 重新获取的信息则直接 Evict。

    像 Code、PRD、RFC 这些 Artifact 本身在 Git Workspace，所以 Context 里只需要保留必要引用和当前相关片段，需要时重新读取，而不是长期携带全文。

    本质上 Context 不是完整执行历史，而是当前这一步继续做正确决策所需要的 Working Set。

  18. 028为什么 Workspace Agent 要把 Workflow Agent 和 Node Conversation Agent 拆开？两者的职责、Context 和 ReAct Loop 有什么区别？

    我们把 Workflow Agent 和 Node Conversation Agent 分开，核心原因是两个 Agent 的定位和运行模式差别比较大。

    Workflow Agent 是围绕研发 Workflow 执行的。比如 PRD、RFC、Plan，每个 Node 都有比较明确的职责、输入和预期输出，同时还受到 Workflow State、SOP 和节点流转规则的强约束。所以它本质上是一个任务执行型 Agent，目标是把当前 Node 稳定执行完成，然后推动整个 Workflow 往下走。

    Node Conversation Agent 不一样，它是一个节点内的对话型 Agent。比如 Workspace Agent 已经生成了一份 PRD，用户可能继续问“支付模块为什么这么设计”，也可能说“把退款这一部分重新生成一下”，甚至只是围绕当前 PRD 做讨论。

    这种交互本身比较开放，没有固定的执行 SOP，也不一定每次都产生新的 Artifact。它主要基于当前 Node 已经生成的 Artifact、节点对话历史、用户最新 Query，以及必要的 RAG / Repository Evidence，动态构造 Context，然后通过自己的 ReAct 去完成这一轮对话。

    所以我不会强行让 Workflow Agent 同时承担这两种模式。Workflow Agent 更强调流程约束和确定性的输入输出，Node Conversation Agent 更强调围绕当前 Artifact 的开放式交互。

    两者最终通过 Artifact 联系起来：Workflow Agent 负责生成和推进 Artifact，Node Conversation Agent 围绕 Artifact 继续讨论和迭代；确认后的 Artifact 再作为后续 Workflow Node 的事实输入。

  19. 029多轮对话中，Agent 最难学习的核心能力是什么？

    我认为多轮对话最难的是 Context Management，而不是单纯保存 Chat History。核心是随着对话增长，Agent 能不能持续识别当前有效的目标、约束和状态，并只获取当前任务真正需要的历史信息。

    在我们的 Workspace 场景里，我会把 Conversation 和 Workflow Node 绑定。比如 PRD Node 的对话主要围绕当前 PRD Artifact 迭代，Context 重点是当前 Artifact、当前 Node State、节点内 Conversation 和最新 Query；跨节点的信息则尽量通过已经确认的 Artifact 传递，而不是把之前所有 Conversation History 全量带过去。

    这样既减少长上下文带来的 Token 成本和噪声，也能降低不同阶段历史对当前 Agent Reasoning 的干扰。

三、Task Understanding

  1. 031Agent 的 Eval 应该怎么做？你怎么评估一个 Agent 到底是“变好了”还是“变差了”？

    我们不会只用最终结果判断 Agent 好不好，而是把整个 Agent 执行链路拆开做分层 Eval。

    第一层是 Task Understanding Eval，判断 Agent 有没有正确理解用户任务，比如 intent、businessDomain、约束条件等结构化字段是否正确。我们这里主要看 Task-level Exact Match，目前大概是 97.2%。

    第二层是 Tool Selection Eval，判断 Agent 在当前任务和 Context 下有没有选择正确的 Tool，目前准确率大概是 95.4%。

    再往后可以看 Execution / Trajectory，比如 Tool 调用是否成功、有没有重复调用、执行顺序是否合理、是否出现无效循环，以及任务有没有正常收敛。

    最后才是 End-to-End Eval，判断整个任务最终有没有完成，以及生成的 Artifact 或 Answer 是否满足预期。

    这样做最大的价值不是指标更多，而是出现 Bad Case 时可以定位到底是 理解错了、Tool 选错了、执行过程错了，还是最终生成错了，然后针对对应环节优化。

    “局部指标负责定位问题，End-to-End 指标负责判断系统整体是否真的变好。”

  4. 055Tool Router 和 Tool Runtime 为什么还要拆成两层？
    Router 已经拿到了 toolName + arguments，它自己直接调用 MCP / Function / RAG 不就行了吗？为什么还要单独设计 Runtime？

    我把 Tool Router 和 Tool Runtime 拆开，本质上是职责划分。

    Tool Router 是一个门控和治理层，它会和上层业务策略有一定耦合，比如当前 Agent、Workspace 或用户有没有权限调用这个 Tool，是否超过 Scope，风险等级是什么，是否需要 Human Approval。

    但 Tool Runtime 我希望它保持成一个比较纯粹的执行层。它只关心已经被允许执行的 Tool Call 应该通过哪个 Provider、哪个 Executor 去执行，以及怎么把执行结果标准化返回，不应该再掺杂业务权限和能力判断。

    这样 Router 的 Policy 可以独立演进，Runtime 的 Provider 也可以独立扩展。以后增加新的 MCP、Function 或 Code Executor，不需要修改上层的权限治理逻辑；反过来修改鉴权和风险策略，也不需要影响底层执行实现。

    从 Agent 架构角度看，MCP 和普通 Function Tool 到底是什么关系？为什么你没有把 MCP 单独设计成 Agent 的一层？

    总结一句：MCP 更本质的区别是它提供了一套标准化的 Tool 暴露和调用协议，让 Tool Provider 和 Agent Runtime 解耦。从 Agent 的视角来看，MCP Tool 和 Function Tool 最终都只是可调用的 Tool，所以我不会在 Agent Reasoning 层把 MCP 单独设计成一层。

    它们主要区别在 Tool 的提供和执行方式。Function Tool 通常是我们在应用内部直接注册的能力，和当前 Runtime 集成比较直接；MCP 则通过标准协议把 Tool Provider 和 Agent 解耦，更适合把一组能力作为独立服务暴露，让不同 Agent 或客户端复用。

    Router 完成鉴权后，Runtime 再根据 Registry 里的 Provider 信息决定走 MCP Executor 还是 Function Executor。

    我们多个 Agent 共用同一套 Tool Infrastructure，但是不同 Agent 的 Tool 权限是不一样的。

    实际实现里，我们会给不同 Agent 分配对应的来源标识 source。Agent 发起 Tool Call 时必须把 source 一起传给 Tool Router。

    权限规则本身不是维护在 Agent Prompt 里面，而是维护在 Tool Router 侧，并通过 Apollo 做动态配置。Router 收到 Tool Call 后，根据 source 查询对应的权限配置，判断这个来源是否允许调用当前 Tool，通过以后才会进入 Tool Runtime 执行。

    比如 Workflow Agent 和 Node Conversation Agent 虽然都可以使用统一的 Tool Catalog 和 Runtime，但它们对应不同的 source，所以 Router 可以给它们配置不同的 Tool 权限集合。

    所以我们的原则是：Agent 决定想调用什么，Router 根据调用来源决定允不允许执行。

五、RAG 底座

  1. 072介绍一下你们完整的 RAG Pipeline / RAG 底座是怎么设计的？

    知识入库（离线阶段）

    知识入库这块，我们目前主要处理归档后的 PRD 和 Summary。

    文档进来以后首先做解析和 Chunk。因为主要是 Markdown 文档，所以我们不是简单按照固定 Token 长度硬切，而是优先按照 Markdown 结构和语义段落切分，尽量保证一个 Chunk 内语义完整；相邻 Chunk 目前保留大约 10% overlap，主要降低边界信息被切断的问题。

    Chunk 完成以后，我们使用本地部署的 BGE Embedding Model 做向量化。选择本地部署主要是考虑内部文档的数据安全，同时模型服务也可以统一控制。

    每个 Chunk 除了正文和 Embedding，还会保存 Metadata，比如 workspaceId、doc_type、version、status、effective_from 等。这样在线检索时可以先根据 Workspace、文档类型或者版本范围做 Metadata Filter，而不是把所有 Workspace 的知识一起召回以后再处理。

    最终同时建立 Dense Retrieval 所需要的向量索引，以及 BM25 所需要的关键词索引，供在线 Hybrid Retrieval 使用。

    在线检索（在线阶段）

    在线阶段拿到 Query 以后，我们不会一开始就调用模型做 Query Rewrite，因为这样会增加延迟和成本。

    首先会尝试匹配已有的业务 Query Expansion Rule，能够命中就做规则扩写，命不中就直接使用原 Query。

    然后进入 Hybrid Retrieval，同时走 BM25 和 Dense Retrieval。两路结果通过 Weighted RRF 做融合，再结合 Workspace 知识的版本信息做 Version-aware Ranking，让当前有效版本优先。

    之后进入 Rerank，对候选文档做更精细的 Query-Document 相关性判断，最终取 Top 5。

    如果 Rerank 后的相关性分数比较低，我们不会立即认为知识库没有答案，而是进入一次 Recall Recovery：调用小模型做 Query Rewrite，然后重新执行检索链路。

    如果二次检索仍然低于阈值，就认为当前知识库无法可靠召回相关资料，不继续生成。

    如果 Retrieval Score 达标，还会经过最后一道 Retrieval Gate。因为相关性高不代表这些 Evidence 就足以回答用户问题，所以 Gate 会结合 Query 和 TopK Evidence 判断当前资料是否充分、是否存在明显冲突等。通过以后才把 Context 交给下游 Agent；不通过就返回知识不足，而不是让模型基于不充分资料强行回答。

    延伸追问08 QUESTIONS
    01你们已经用了 Reranker，而且还设置了 Score Threshold。为什么后面还需要一个 LLM Retrieval Gate？

    一句话总结：Reranker 解决“找得像不像”，Gate 解决“这些东西够不够回答”。

    Reranker 和 Retrieval Gate 解决的是两个不同层次的问题。

    Reranker 判断的是 Relevance，也就是“检索内容和 Query 有多相关”；Retrieval Gate 判断的是 Sufficiency，也就是“当前 Evidence 是否足以支持回答这个 Query”。

    相关性高并不代表能够回答问题。

    比如用户问“公司是否支持跨门店退款”，召回了“退款支持原路退款和余额退款”和“跨门店订单支持查询”。这两条资料分别和“退款”“跨门店”高度相关，所以 Reranker 完全可能给出不错的相关性分数，但两条 Evidence 都没有明确说明“跨门店是否支持退款”。

    如果 RAG 底座直接把这些资料返回给上层 Agent，相当于把 Evidence 不充分的风险外抛给了调用方。上层 LLM 很可能把两条相关信息组合起来，推断出一个知识库实际上没有支持的答案。

    所以我们最后增加 Retrieval Gate，判断 TopK Evidence 是否真正能够支撑回答当前 Query。只有通过 Gate 才返回 Context，否则明确返回 Knowledge Insufficient。

    对我们来说，RAG Platform 的契约不是“尽可能返回一些相关资料”，而是尽可能返回能够支撑回答的可靠 Evidence。

    02但你这个 Gate 如果也是一个 LLM Judge，它本身也会误判。比如明明 Evidence 足够，它判断不足；或者 Evidence 明明不够，它却判断可以回答。那你怎么评估这个 Retrieval Gate 本身准不准？

    Gate 本身也是一个模型能力，所以不能默认它是可靠的，我们会单独给 Gate 建 Eval Dataset。

    测试集里会明确标注 Query + Evidence，以及 sufficient / insufficient 的 Ground Truth，然后离线跑 Gate，统计 Precision、Recall、F1，同时重点分析 False Positive 和 False Negative。

    对 Gate 来说我会更关注 Precision，因为它是 RAG 输出给上层 Agent 之前的最后一道可靠性门禁。

    False Positive 意味着 Evidence 明明不足，Gate 却放行了，这会把不可靠 Context 交给生成模型，最终可能产生没有证据支撑的回答；False Negative 虽然也不好，但主要影响的是 Answer Rate——知识库其实能回答，但是我们选择拒答。

    所以在可靠性优先的企业知识场景里，我会更倾向于降低 False Positive，即使牺牲一部分 Recall。

    03你刚才说通过测试集计算 Gate 的 Precision 和 Recall。那这个测试集的 Ground Truth 怎么来的？

    val Dataset 我们不是全部让 LLM 自动生成，而是分层建设。

    第一部分是核心 Gold Dataset，主要来源于公司真实产品答疑场景。我们从商家、客户成功等真实问题里提取 Query，再结合产品文档以及已经确认过的业务答案，由人工整理 Ground Truth。

    这部分重点不是追求数量，而是保证真实性和标注质量，同时尽量覆盖主要业务场景。

    第二部分会人工补充一些正常线上数据里比较少见、但对 Gate 很重要的边界和异常 Case，比如 Knowledge Base 完全没有答案、Evidence 只回答了一半、Evidence 看起来高度相关但实际上无法回答、不同版本 Evidence 冲突等。

    在核心数据之外，我们再通过 LLM 做 Synthetic Data Expansion，比如对已有 Query 做改写、构造不同表达方式以及生成边界 Case，提高测试集覆盖度。

    但 Synthetic Case 不会和人工 Gold Case 完全等价使用。我们会做人工抽检，核心场景和高风险 Case 会有更严格的人工确认。

    04那假设现在出现这样一个情况：Recall@5 = 96%，MRR@5 = 0.86，看起来 Retrieval 都很好，但最终 Answer Accuracy 只有 85%。你会怎么定位这 11% 的 Gap？

    指标告诉我哪一层可能有问题，Bad Case Trace 才告诉我具体为什么错

    如果 Retrieval 指标都比较好但 Answer Accuracy 明显偏低，我不会直接认为是生成模型的问题，而是会把 Answer Wrong 的 Case 单独拿出来做 Pipeline 级归因。

    首先确认 Gold Evidence 是否真的进入 TopK；如果进入了，再人工或者通过标注判断这些 Evidence 是否足以回答问题。如果不够，就继续看知识缺失、Chunk、版本冲突、冗余召回等问题。

    如果 Evidence 本身足够，再检查 Gate 的判断是否正确，而不是只看 Gate Score，因为 Gate 本身也可能产生 False Positive。

    Gate 没问题以后，再检查 Context Assembly，比如是否混入旧版本、冲突资料、无关 Chunk，或者关键 Evidence 在组装过程中被丢掉。

    如果最终传给 Generation 的 Context 是正确且充分的，但答案仍然错误，这时候才归因到 Generation，再针对 Prompt、Context 组织方式或者模型能力优化。

    05你刚才多次提到“版本冲突”。假设知识库里同时存在：
    v1.0：退款需要人工审核。
    v1.5：退款已经支持自动退款。
    用户只问：“退款需要审核吗？”
    两个版本都可能被 Dense 和 BM25 召回。
    你们具体怎么做 Version-aware Retrieval / Ranking？为什么不直接在 Metadata Filter 阶段只保留最新版本？

    我们不会在 Metadata Filter 阶段直接过滤成最新版本，因为 Workspace 的 RAG 本身承担了历史知识库的作用，需要保留知识演进时间轴。

    比如 v1.0 是人工审核，v1.5 改成自动退款。如果用户问“现在退款需要审核吗”，我们希望最新版本优先，但历史版本仍然可以作为补充 Evidence，让模型回答“当前已经支持自动退款，历史版本需要人工审核”。

    同样，如果用户明确问“v1.0 是怎么处理的”或者“之前是不是需要审核”，系统也能够直接检索历史版本。

    所以我们不会把 Version 当成简单的 Hard Filter，而是结合 Query Intent 做 Version-aware Ranking。

    06现在模型本身已经支持 Function Calling / Tool Calling，理论上完全可以把所有 Tools 注册给 LLM，让 Agent Reasoning 自己选择。那为什么你的系统还要设计分层 Tool Catalog / Registry 和 Tool Router？为什么不直接把所有 Tools 一次性暴露给 LLM？Tool Router 又解决了什么问题？

    模型支持 Function Calling，不代表应该把所有 Tool 一次性暴露给模型。我的设计里没有再单独做 Capability Planning，而是保留分层 Tool Catalog，让 Agent Reasoning 在每轮 ReAct 中先根据当前状态选择工具分类，再按需展开具体 Tool，从而减少 Tool Schema 的上下文占用和 Tool Selection 的搜索空间。

    Agent 选定具体 Tool 后，再经过 Tool Router。Router 不参与语义决策，而是作为统一治理层，负责注册管理、参数校验、权限鉴权、风险策略和审计，通过后交给 Tool Runtime 执行。

    所以本质上是：Agent Reasoning 解决“现在该调用什么”，Tool Catalog 解决“不要一次看到所有工具”，Tool Router 解决“这个调用能不能执行”，Tool Runtime 解决“具体怎么执行”。

    07你现在把 MCP、Function Tool、RAG、Code Execution 全部统一到了 Tool Router。
    但这些能力的调用模型完全不一样。
    Function Tool 是一次 RPC 风格调用；RAG 可能有 Query Rewrite → Retrieval → Rerank → Gate；Code Execution 甚至可能是长时间、有副作用的操作。
    你怎么设计 Tool Router 的统一接口？怎么避免为了“统一”而把不同能力强行抽象成一个很别扭的 execute(tool, args)？

    Tool Router 的设计思路其实和 MCP Server 比较像，核心目的都是把底层能力标准化暴露出去，让上层 Agent 不需要关心具体实现。

    区别是我们的 Router 管理范围更广。MCP 只是其中一种接入协议，除了 MCP Server，我们还可以把 Function Tool、RAG、Repository Search、Code Execution 等内部能力统一注册进 Router。

    每个能力只需要满足 Router 约定的输入输出协议，就可以接入。Agent 最终面对的是统一的 Capability Interface，而不是分别适配 MCP、RAG 或内部函数。

    08如果 Agent 在一次任务里需要连续调用多个 Tool，你怎么处理 Tool 之间的依赖关系和并行关系？
    比如“按照 Figma 修改商品详情页按钮”这个任务，可能涉及 search_code、read_file、figma_get_design_context、edit_file、run_test、visual_compare。
    哪些可以并行，哪些必须串行？这个调用顺序是谁决定的？你会不会一开始就生成完整的执行 DAG？

    不会一开始生成完整 DAG，因为很多 Tool 的后续调用依赖前一步的 Observation，一开始并不知道完整执行路径。

    我会让 Agent Reasoning 在每轮 ReAct 中，根据当前 State 和已有 Evidence，生成一个局部的执行 Plan，并分析当前几个 Tool Call 之间的依赖关系。

    如果多个 Tool 没有数据依赖，就可以在当前 Loop 中并行调用；如果后一个 Tool 依赖前一个 Tool 的结果，就串行执行。

    Agent Reasoning 负责决定并行还是串行以及调用哪些 Tool；Tool Router 只负责对这些 Tool Call 逐个做权限、参数和风险校验，通过后交给 Tool Runtime 执行。

  2. 073现在用户向 Agent 提了一个业务问题，Query 进入 RAG 以后：
    从 Query Processing 开始，到最终把 Evidence 返回给 Agent，你们完整的在线检索链路是什么？
    重点讲清楚 Query Rewrite、混合检索、RRF、Rerank，以及你们为什么还需要 Retrieval Gate。

    Query 进入 RAG 后，首先做 Query Processing。如果是节点内多轮对话，会结合 Conversation Context 做指代补全，把 Query 还原成相对完整、可独立检索的问题；然后命中已有业务规则时做规则型 Query Rewrite。

    接下来进入 Hybrid Retrieval，通过 BM25 和 Dense Retrieval 双路召回，再使用 RRF 做排序融合，并通过 MMR 降低 TopK 中语义高度重复的 Evidence。

    如果第一轮 Retrieval Confidence 不满足阈值，不会直接返回空，而是触发第二级 Query Rewrite，通过小模型对 Query 做扩写或改写，然后重新执行检索；如果第二轮仍然不满足阈值就终止，并记录 Bad Case，进入后续 Eval 和优化。

    召回通过后进入 Rerank，对候选 Evidence 做更精细的相关性排序。

    最后还有 Retrieval Gate。因为相关性高并不意味着 Evidence 足以回答问题，所以 Gate 会结合 Query 和 Top Evidence 判断当前证据是否具有足够的支持度。通过才把 Evidence 返回给上层 Agent，否则返回 Knowledge Insufficient，而不是让上层模型基于相关但不充分的信息强行生成答案。

  3. 074为什么 Workspace Agent 需要自己建设 RAG 底座？
  4. 075你的 RAG 底座整体架构是什么？
  5. 076哪些数据进入 RAG，哪些数据不进入？
  6. 077为什么 PRD 和 Summary 入库，而 RFC / Plan / Code 不一定入库？
  7. 078数据从原始文档到最终可检索 Chunk 的完整 Pipeline 是什么？

    我们知识入库主要处理已经归档的 PRD、Summary 和业务规则。

    首先对文档进行解析和清洗，同时整理 workspaceId、businessDomain、doc_type、version、status、effective_from 等 Metadata。

    文档主要是 Markdown，所以 Chunking 这一层我们没有直接依赖 Milvus，而是自己实现了 Markdown Chunker，通过正则识别 Markdown 的标题、段落等结构进行切分，尽量按照文档的语义结构生成 Chunk，而不是简单按照固定字符数截断。

    得到 Chunk 后，使用 BGE Embedding Model 对每个 Chunk 的 content 生成 Dense Vector，然后将 chunkId + content + metadata + dense vector 写入 Milvus。

    Milvus 侧建立 Dense 和 BM25/Sparse 检索能力。在线查询时分别进行 Dense Retrieval 和 BM25 Retrieval，再通过 RRF 融合，进入后续 MMR、Rerank 和 Retrieval Gate。

  8. 079Chunk 怎么切？

    默认以 500 字符为分块目标，仅当一个完整章节或段落超过 500、但不超过 1000 时，才允许整块保留。 不主动把多个独立内容拼到 1000。

    具体规则：

    1. 从大到小检查标题层级
      • 完整模块 ≤500：整块保留。
      • 完整模块 >500 且 ≤1000：为保留完整性，整块保留。
      • 完整模块 >1000：按下一级标题拆分，递归应用同样规则。
    2. 没有子章节时，按段落处理
      • 相邻的小段落在同一标题下，可以合并，合并目标为 500。
      • 单个完整段落 >500 且 ≤1000：单独保留。
      • 单个段落 >1000：优先按句子切分，目标为 500；超长单句再用字符窗口切分。
    3. 保留标题和上下文
      • 每块携带标题路径，长度计算包含标题前缀。
      • 仅在长内容被拆开时保留约 50 字符重叠，即默认窗口的 10%；独立章节之间不强加重叠。
      • 父章节正文、子章节内容都必须保留，避免遗漏。

    实现采用 Markdown 标题树＋递归长度判断＋段落/句子切分，无需引入 LLM。

  11. 082为什么使用 BM25 + Dense Retrieval？

    BM25 和 Dense Retrieval 的原始 Score 不在同一个分数空间，所以不能简单直接相加，否则某一路可能因为 Score 数值范围更大而主导结果。

    我们使用 RRF 做融合。RRF 不依赖不同检索器的原始 Score，而是根据文档在各路召回结果中的 Rank 计算融合分数：Σ 1 / (k + rank)。

    一个 Chunk 如果同时被 BM25 和 Dense 召回，并且两边排名都比较靠前，它最终的 RRF Score 就会更高。

    这样可以比较低成本地融合不同类型检索器，也避免了不同 Score 体系之间做复杂归一化的问题。

    再记一句最核心的：

    RRF 融合的是 Rank，不是原始 Score，因此天然规避了 BM25 和 Dense Score 不同尺度的问题。

  13. 084MMR 是什么？为什么 RRF 后还需要 MMR？

    RRF 主要解决 BM25 和 Dense Retrieval 两路召回结果的 Rank Fusion 问题，但它并不能解决召回结果之间的内容冗余。

    比如一个问题可能召回多个语义高度相似的 Chunk，如果全部进入后面的 Rerank 和生成阶段，不仅浪费 Context Window，也可能把其他有价值的 Evidence 挤出 TopK。

    所以我们在 RRF 之后使用 MMR。MMR 在选择候选 Chunk 时，同时考虑它与 Query 的相关性以及它和已经选中 Chunk 的相似度，在相关性和多样性之间做平衡。

    简单来说，RRF 负责融合多路 Retrieval 的排序，MMR 负责降低候选 Evidence 之间的冗余。

    还有一个容易被追问的点：

    MMR 不是简单的“相似度 > 0.9 就删除”。 它是在相关性和多样性之间做 trade-off，所以相比硬阈值 Semantic Dedup，更不容易直接误删有价值的 Evidence。

  21. 092Rerank 和 Embedding 相似度检索有什么区别？

    Dense Retrieval 一般是 Bi-Encoder / 双塔结构，Query 和 Chunk 分别编码成向量，然后通过向量相似度进行检索。它的优势是 Chunk 的 Embedding 可以提前计算并建立索引，所以检索速度非常快，适合从海量数据中做第一阶段召回。

    Rerank 通常使用 Cross-Encoder，把 Query 和候选 Chunk 一起输入模型，让模型同时看到两边的信息，通过更细粒度的交互判断 Query 和 Chunk 的相关性，因此相关性判断通常比单纯的向量相似度更准确。

    但 Cross-Encoder 没办法像 Embedding 一样提前把所有 Chunk 编码后直接做 ANN 检索，每个 Query × Chunk 都需要单独计算，所以计算成本更高。

    因此我们不会让 Reranker 扫整个知识库，而是先通过 BM25 + Dense → RRF → MMR 缩小候选集，再让 Reranker 对候选 Chunk 做精排。

    一句话记住：

    Bi-Encoder 用于大规模“召回”，Cross-Encoder 用于小候选集“精排”。

十一、AI Code Review

  1. 173AI Code Review 为什么值得用 LLM 做？

    ESLint、SonarQube、TypeScript 这类传统工具，本质上更擅长基于确定性规则做静态检查，比如语法、类型、安全规则、代码规范等，这类问题其实没必要交给 LLM。

    但真实 Code Review 还有大量需要结合上下文才能判断的问题。比如这次修改的业务逻辑是否正确、有没有遗漏相关调用方、修改一个公共方法后有没有影响其他模块、实现是否符合 Repository 里的业务规则等。

    LLM 的价值主要在这里：它可以结合 Diff + Repository Context + 业务 Rules 做语义级的代码理解，补充传统静态分析覆盖不到的问题。

    所以我们的定位不是用 LLM 替代 ESLint 或 SonarQube，而是让两者形成互补：确定性问题交给静态分析，语义和上下文相关的问题交给 LLM。

  2. 174一次 Code Review 的完整 Pipeline 是什么？

    我们的 AI Code Review 是异步任务架构。首先 Review 平台发起审核请求，携带 projectId、branch 等信息，平台层不会同步执行，而是把任务写入任务队列，由后面的 Worker 调度执行。

    Worker 拿到任务以后，首先准备 Repository Context。检查本地是否已经存在对应仓库，如果存在就更新代码，否则拉取仓库，然后切换到目标分支，通过 Git 获取本次变更的 Diff。

    拿到 Diff 后不会直接全部塞给 LLM，而是先做依赖分析和 Context 构建，找到与本次修改相关的代码；然后根据模型 Context Window 和 Token Budget 对变更进行分组。

    Context 准备完成后，对可以独立处理的 Group 做并发审核。这里我们主要有两类任务：代码审核评论和影响面分析。

    模型执行完成以后不会直接把结果发布出去，还会做一次文件完整性和结果校验，确认 Comment 对应的文件、代码位置以及结果结构合法。

    校验通过以后，再把最终 Review 结果回写到 GitLab 对应的 MR。

  3. 175Diff 太大超过 Context Window 怎么办？

    “我们的目标不是让每个 Group 尽可能小，而是在 Token Budget 约束下，尽可能保留一个完整的 Dependency Context。”

    大型 MR 超过 Context Window 时，我们不会简单按照文件切分，而是先对变更文件做依赖分析，建立文件之间的依赖关系。

    然后基于依赖关系构建分组，在模型的 Token Budget 范围内，尽可能把存在强依赖关系的文件放在同一个 Review Group 中。

    分组过程是从较高层级开始判断，如果一个依赖子树整体超过 Context Window，就递归向下拆分，直到得到满足 Token Budget 的最小可审核分组。

    最后不同 Group 可以批量、并发请求 LLM 做 Review。

    不能简单一个文件一个文件 Review，是因为很多问题只有结合跨文件上下文才能发现。比如修改了一个公共方法，同时修改了调用方；如果两个文件被完全独立审核，模型可能看不到完整的依赖关系，从而漏掉接口不一致、调用方遗漏或者影响面问题。
