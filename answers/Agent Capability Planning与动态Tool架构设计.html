Agent Reasoning
与分层 Tool 架构设计

Task Understanding 明确任务；Agent Reasoning 每轮查看一级 Capability Catalog，按需加载具体工具并发起调用；Router 统一管理、鉴权和执行策略。

1. 核心结论

Task Understanding 先提取用户目标、约束和完成标准。随后 Agent Reasoning / ReAct 进入循环：每轮都能看到完整的一级 Capability Catalog，判断下一步需要什么 Capability，动态加载其下的 Tools，再选择具体工具和参数。这里不再单设 Capability Planning。

工具选择与调用顺序属于 Agent Reasoning；Tool Router 负责工具统一管理、鉴权和 Policy，不替 Agent 选择工具。

text
Task Understanding
        ↓
Agent Reasoning / ReAct（每轮可见完整一级 Capability Catalog）
        ├─ 判断下一步需要什么 Capability
        ├─ 动态加载该 Capability 下的 Tools
        └─ 从具体 Tools 中 Function Calling
        ↓
Tool Router（管理 / 鉴权 / Policy）
        ↓
Tool Runtime → Result → Observe ──→ Agent Reasoning / ReAct

Capability 是 Agent 每轮可见的一级分类。Tool 是展开选定分类后可供调用的具体动作。MCP、Function、RAG、Code、Browser 是工具的来源或执行方式。

2. Task Understanding 与任务约束

把商品详情页的按钮样式按照 Figma 修改一下，不要修改公共 Button 组件。

Task Understanding 识别目标、设计来源、禁止改动范围和完成标准，并把这些信息交给 Agent Reasoning。Reasoning 不能只根据任务文字立即调用 edit_file：先找到代码和设计信息，确认实现位置后才能修改，修改后还要验证。

text
目标：商品详情页按钮与 Figma 一致
约束：不能修改公共 Button
完成条件：代码检查通过，页面效果与设计一致

3. 每轮可见的 Capability Catalog

每轮 Agent Reasoning 都能看到完整的一级 Capability Catalog，例如 repository、design、knowledge、code、browser、git。一级只包含分类名称和能力描述，不预先展开所有工具 schema。Agent 判断当前需要哪个 Capability 后，才动态加载该分类下可用的具体 Tools、schema、风险和前置条件。

text
repository → search_code / search_symbol / read_file / read_directory
design     → figma_get_design_context / figma_get_screenshot
knowledge  → search_prd / search_doc
code       → edit_file / create_file / run_lint / run_typecheck / run_test / run_build
browser    → start_dev_server / browser_screenshot / visual_compare
git        → git_status / git_diff / git_commit

完整的一级目录在每轮都可见；二级 Tools 按 Agent 当前选择动态加载。这不是 Router 预先挑选候选工具，也不是初始化时冻结一个 Capability Scope。

4. Agent Reasoning 的职责

  • 接收 Task Understanding 产出的目标、约束和完成标准。
  • 每轮查看完整一级 Capability Catalog，判断下一步需要哪个 Capability。
  • 动态加载所选 Capability 下的 Tools，选择具体 Tool、填写参数，并判断调用依赖。
  • 从具体 Tools 中 Function Calling；观察 Result 后决定继续查询、修改、验证、重试或结束。
text
当前缺少代码位置 → 选择 repository → 加载 Tools → 调用 search_code
搜索结果指向 ProductAction → 再看完整目录 → 选择 repository → 调用 read_file
确认业务层修改点且读到 Figma → 选择 code → 加载 Tools → 调用 edit_file

这些判断发生在同一个 Agent Reasoning 循环里；不需要在它前面再运行一次 Capability Planner。

5. 依赖顺序与并行边界

工具调用不是独立的扁平清单。Agent 应依据证据和前置条件构建当前任务的依赖关系；只有不存在依赖的步骤才适合并行。

text
search_code ─→ read_file ───────────┐
                                  ├─→ 判断修改点 ─→ edit_file ─→ run_test ─→ visual_compare
figma_get_design_context ────────┘

上例中读取 Figma 可以与搜索或读代码并行；edit_file 必须等代码与设计依据齐备。测试和视觉验证必须基于修改后的代码。如果测试失败，Agent 回到推理循环调整后续步骤。

某些工具本身也有前置条件，例如 browser_screenshot 需要开发服务已启动，读取文件需要先获得路径。这些依赖应通过工具元数据和执行结果让 Agent 可见。

6. 动态加载 Tools 与 Registry

Capability Catalog 提供始终可见的一级分类；Tool Registry 维护每个分类下的具体 Tools、schema、风险和 Provider 元数据。Agent 选定分类后，系统从 Registry 动态加载该分类的 Tools，供 Agent 继续选择。Router 使用同一份元数据做管理与鉴权，Runtime 用它定位执行器。

json
{
  "name": "figma_get_design_context",
  "category": "design",
  "description": "读取 Figma 节点的设计上下文",
  "schema": {"node_id": "string"},
  "provider": "mcp",
  "server": "figma",
  "risk": "read",
  "prerequisites": ["figma_connection"]
}

分类是发现入口，不代表一个分类只能有一个 Tool。同一分类可以容纳不同用途的工具；Agent 查看动态加载的工具描述与 schema 后作具体选择。

7. Tool Router：统一管理与鉴权

Agent 已经选定工具和参数后，Tool Router 接收 Tool Call，通过 Registry 解析工具身份并做统一管理和鉴权。它不依据任务语义替 Agent 换工具，也不决定调用顺序。

text
Agent Tool Call
    ↓
Tool Router
    ├─ 校验工具是否已注册、是否对当前 Agent 可见
    ├─ 校验参数 schema、作用域、身份与权限
    ├─ 应用风险策略：允许 / 拒绝 / 沙箱 / 人工审批
    └─ 记录审计、配额与调用状态
    ↓
Tool Runtime

原文单列的 Tool Policy 可以作为 Router 内部的策略模块，不必再画成与 Router 并列的决策层。权限配置由系统控制，Agent 不能通过选择工具绕过。

8. Function Calling 与参数

Function Calling 是 Agent 从已加载的具体 Tools 中发起调用的形式，不是另一个独立的工具选择者。Agent 看到所选分类下的工具 schema 后，可产生如下调用：

json
{
  "name": "search_code",
  "arguments": {"query": "ProductDetail 商品详情"}
}

Router 校验该调用，Runtime 执行。Tool Result 返回后，Agent 再判断下一步。

9. Tool Runtime 与 Provider

Tool Runtime 根据 Registry 中的 Provider 信息调用对应执行器，屏蔽协议差异；业务推理和工具选择仍由 Agent 完成。

text
Tool Call → Tool Router（管理、鉴权） → Tool Runtime
                                          ├─ MCP Executor → Figma / Jira / GitHub
                                          ├─ Function Executor → 内部函数
                                          ├─ RAG Executor → 文档检索
                                          ├─ Code Runtime → 文件 / 命令
                                          └─ Browser Runtime → 页面操作

Figma MCP Server 是 Provider，不是一个可与 search_code 并列选择的 Tool。Registry 应注册它暴露的具体工具，如 figma_get_design_context。

10. Observe 与动态调整

Agent 收到工具结果后，更新对任务的理解和依赖关系，再选择下一步工具。例如搜索定位到 ProductAction，读取后发现它使用公共 Button；由于用户禁止修改公共组件，Agent 应改为寻找业务层样式入口。

text
Tool Runtime → Result → Observe → Agent Reasoning / ReAct
    ├─ 证据不足 → 再看完整一级目录，按需加载 Tools
    ├─ 前置条件满足 → 调用修改工具
    ├─ 验证失败 → 分析错误、修复并重新验证
    └─ 达到完成标准 → Done

Observe 将执行结果反馈给 Agent Reasoning；下一轮仍可看到完整一级 Capability Catalog。动态调整的是 Agent 的推理与调用计划；Router 对每次调用重复执行统一管理、鉴权和 Policy 检查。

11. 修改后的验证

代码变更不能以 edit_file 返回成功作为完成条件。Agent 应按任务选择有意义的验证工具，并遵循依赖顺序。

text
edit_file → run_lint / run_typecheck / run_test / run_build
          → start_dev_server → browser_screenshot → visual_compare

如果构建失败或截图不符合设计，Agent 读取失败信息，继续修改并重新验证。必要时重新读取源代码或设计信息。

13. 设计原则

  • Task Understanding 位于循环入口。它提供目标、约束和完成标准。
  • 一级目录每轮可见，二级 Tools 按需加载。Agent 最终选择的是具体 Tool。
  • Agent 决定调用顺序。有依赖的调用必须等待前置结果，独立调用才可并行。
  • Router 不做语义选择。它负责统一管理、鉴权、风险策略与审计。
  • Provider 不进入工具选择层。MCP、Function、RAG、Code、Browser 是实现或执行方式。
  • Observe 回到 Agent Reasoning。每轮都能重新查看完整一级目录，不需要初始阶段冻结 Capability Scope。

Agent 选择“做什么、先后怎么做”；Tool Router 决定“这次调用是否被允许”；Tool Runtime 负责“怎样执行”。
