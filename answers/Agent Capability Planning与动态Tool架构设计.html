1. 核心结论

提升 Agent Function Calling 灵活性的关键，不是简单给模型提供更多 Function，而是增加一层 Capability（能力）抽象：

Task Understanding → Capability Planning → Tool Router → Tool Registry → Function Calling → Tool Policy → Tool Runtime → Observe → Re-plan

其中：

  • Capability Planning 不直接感知所有具体 Function。
  • 它只需要知道系统可以提供哪些“能力”。
  • 具体 Function 由 Tool Router / Tool Registry 根据 Capability 动态解析和加载。
  • Capability 相对稳定，底层 Tool 可以持续新增、替换和演进。

这可以避免 Tool 数量越来越多后，把几十甚至上百个 Function Schema 一次性塞给 LLM。

3. Task Understanding

Task Understanding 解决的是：

用户到底想让我完成什么？

它关注的是 What，而不是具体调用什么 Tool。

例如：

text
把商品详情页的按钮样式按照 Figma 修改一下

可以转换为结构化 Task：

json
{
  "intent": "modify_ui",
  "target": {
    "page": "商品详情页",
    "element": "按钮"
  },
  "reference": {
    "type": "figma"
  },
  "change_type": "style",
  "expected_result": "代码实现与 Figma 设计一致"
}

如果用户进一步说：

按照 Figma 修改商品详情页按钮样式，不要修改公共 Button 组件。

则可以得到：

json
{
  "intent": "modify_ui",
  "target": "商品详情页按钮",
  "reference": "figma",
  "constraints": [
    "do_not_modify_shared_button"
  ]
}

因此 Task Understanding 主要负责识别：

  • 用户意图
  • 操作对象
  • 参考信息
  • 用户约束
  • 完成标准

4. Capability Planning

Capability Planning 解决的是：

完成这个任务，需要系统具备哪些能力？

此时不要直接考虑：

text
search_code
read_file
figma_get_node
edit_file

这些都是具体 Tool。

对于当前任务，Capability Planner 可以得到：

json
{
  "required_capabilities": [
    "repository_search",
    "code_read",
    "design_read",
    "code_edit",
    "code_validation",
    "visual_validation"
  ]
}

对应含义：

text
商品详情页按钮样式修改
        │
        ├── repository_search
        │      找到商品详情页相关实现
        │
        ├── code_read
        │      理解当前按钮代码
        │
        ├── design_read
        │      获取 Figma 设计信息
        │
        ├── code_edit
        │      修改业务代码
        │
        ├── code_validation
        │      lint / typecheck / test / build
        │
        └── visual_validation
               验证最终 UI 是否符合设计稿

核心关系：

Capability ≠ Tool

例如：

text
repository_search

是一种能力。

它的实现可以是：

text
ripgrep
Code Search API
GitHub Search
IDE Index
Codex Search

Capability Planner 不应该和具体实现强绑定。

5. Capability Catalog

Capability Planner 需要提前知道系统有哪些能力可以提供。

因此平台可以维护一个 Capability Catalog：

python
CAPABILITIES = {
    "repository_search": {
        "description": "定位仓库中的页面、组件、函数、类型和相关实现"
    },
    "code_read": {
        "description": "读取并理解指定代码文件"
    },
    "design_read": {
        "description": "获取 Figma 设计信息"
    },
    "knowledge_search": {
        "description": "检索 PRD、历史迭代和业务知识"
    },
    "code_edit": {
        "description": "修改或创建代码"
    },
    "code_validation": {
        "description": "执行 lint、typecheck、test、build 等验证"
    },
    "visual_validation": {
        "description": "运行页面、截图并验证 UI 与设计稿的一致性"
    },
    "git_operation": {
        "description": "创建分支、提交代码等 Git 操作"
    }
}

Capability Planner 看到这些 Capability，但不需要看到所有 Function Schema。

6. Tool Registry

Tool Registry 负责维护：

Capability → Concrete Tool

例如：

text
repository_search
├── search_code
├── search_symbol
└── find_reference

code_read
├── read_file
├── read_files
└── read_directory

design_read
├── figma_get_node
├── figma_get_design_context
└── figma_get_screenshot

code_edit
├── edit_file
├── create_file
└── delete_file

code_validation
├── run_lint
├── run_typecheck
├── run_test
└── run_build

visual_validation
├── start_dev_server
├── browser_open
├── browser_screenshot
└── visual_compare

也可以给 Tool 注册 Metadata：

json
{
  "name": "search_code",
  "capability": "repository_search",
  "provider": "code_runtime",
  "risk": "read",
  "description": "Search source code in the current repository"
}

例如：

json
{
  "name": "figma_get_design_context",
  "capability": "design_read",
  "provider": "figma_mcp",
  "risk": "read"
}

这样 Capability Planner 不需要知道 Tool 是通过 MCP、Function、CLI 还是内部 Service 实现的。

7. Capability 稳定，Tool 可变化

这是引入 Capability Layer 最重要的价值之一。

例如今天：

text
repository_search
        ↓
     ripgrep

以后升级为：

text
repository_search
        ↓
Code Index Service

甚至再升级为：

text
repository_search
        ↓
Codex Search

对于 Capability Planner 来说：

text
repository_search

始终没有变化。

因此：

Agent 的任务规划逻辑和底层工具实现解耦。

8. Tool Router

Capability Planner 得到：

text
repository_search
code_read
design_read
code_edit
code_validation
visual_validation

但并不意味着第一次调用 LLM 时，就需要把所有相关 Tool 全部加载。

Tool Router 应根据 Agent 当前状态动态选择工具。

例如任务刚开始：

text
当前不知道代码在哪里
当前不知道 Figma 设计是什么

此时只需要：

text
repository_search
code_read
design_read

Tool Router 再从 Registry 中加载：

text
search_code
read_file
figma_get_design_context
figma_get_screenshot

而不需要加载：

text
edit_file
run_build
git_commit
create_pr
deploy
send_email
query_database
...

这样可以显著缩小 LLM 当前的 Tool Selection Space。

9. Function Calling

到了这一层，LLM 才真正看到具体 Function。

例如：

text
search_code
read_file
figma_get_design_context

LLM 根据当前上下文判断：

我还不知道商品详情页实现在哪里，所以先搜索代码。

产生：

json
{
  "name": "search_code",
  "arguments": {
    "query": "ProductDetail 商品详情"
  }
}

三层职责需要明确区分：

text
Capability Planning
↓
“我需要 repository_search 能力”

Tool Registry
↓
“repository_search 可以由 search_code 提供”

Function Calling
↓
“当前调用 search_code，参数为 ProductDetail”

10. Tool Policy

Tool 被选中以后，不应该立即执行。

应该先经过 Tool Policy。

例如按照风险划分：

text
READ
├── search_code
├── read_file
├── search_prd
└── figma_read

WRITE
├── edit_file
└── create_file

EXECUTE
├── run_test
├── run_build
└── run_command

EXTERNAL_WRITE
├── git_push
├── create_pr
└── create_jira

DANGEROUS
├── delete_repository
├── deploy_production
└── destructive_database_operation

执行链路：

text
LLM Tool Selection
        │
        ▼
    Tool Policy
        │
        ├── Allow
        ├── Deny
        ├── Sandbox
        └── Human Approval
        │
        ▼
    Tool Runtime

核心原则：

LLM 决定“想做什么”，系统决定“允许做什么”。

不要完全依赖 Prompt 告诉 LLM“不要执行危险操作”。

11. Tool Runtime

Tool Runtime 只负责真正执行 Tool。

例如：

python
result = search_code(
    query="ProductDetail"
)

返回：

text
src/pages/product/detail/index.tsx
src/components/ProductAction/index.tsx
src/components/Button/index.tsx

Tool Runtime 本身不负责业务推理。

职责应该保持简单：

text
Tool Arguments
      ↓
Execute
      ↓
Tool Result

12. Observe 与 Re-plan

Tool 执行完成不意味着任务完成。

Agent 需要理解结果。

例如 search_code 返回：

text
src/pages/product/detail/index.tsx
src/components/ProductAction/index.tsx
src/components/Button/index.tsx

Agent Observe 后得到：

text
ProductAction 很可能是商品详情页操作按钮的实现。
但是还没有确认具体代码。

于是 Re-plan：

text
下一步：

1. read_file(ProductAction)
2. 获取 Figma Design Context

这两个任务如果不存在依赖，可以并行：

text
                 Agent
                   │
          ┌────────┴────────┐
          ▼                 ▼
 read ProductAction     read Figma
          │                 │
          └────────┬────────┘
                   ▼
                 Observe

假设代码当前为：

css
.buyButton {
    height: 40px;
    border-radius: 4px;
}

Figma 为：

text
height: 44px
border-radius: 8px
font-size: 16px
padding: 0 24px

Agent 此时才真正具备修改依据。

然后进入：

text
code_edit

Tool Router 可以动态把当前 Tool Set 调整为：

text
read_file
edit_file

13. Capability Planning 不应该变成固定 Workflow

一个重要误区是：

Capability Planner 输出：

json
{
  "steps": [
    "repository_search",
    "code_read",
    "design_read",
    "code_edit",
    "code_validation"
  ]
}

然后系统机械执行：

text
1 → 2 → 3 → 4 → 5

这会重新退化成传统 Workflow。

Agent 的优势在于执行过程中可以根据 Observation 动态调整。

例如读取代码以后发现：

text
Button 来自 @company/design-system

并且公共 Button 不允许修改。

那么原计划可能需要调整为：

text
read dependency
      ↓
理解 Design System 使用方式
      ↓
确认不能修改公共组件
      ↓
寻找业务层扩展方式
      ↓
修改 ProductAction className

因此 Capability Planning 更适合回答：

完成当前 Task 可能需要哪些能力？

而不是：

未来必须严格按照哪些步骤执行？

真正执行顺序应该由 Agent Loop 动态决定。

14. Agent Loop

推荐执行模型：

text
Task
 │
 ▼
Capability Planning
 │
 ▼
Available Capability Scope
 │
 ▼
Agent Reasoning
 │
 ▼
Tool Call
 │
 ▼
Tool Runtime
 │
 ▼
Observe
 │
 ▼
Agent Reasoning
 │
 ├── 需要更多信息 → Tool Call
 │
 ├── 需要修改 → Tool Call
 │
 ├── 验证失败 → Re-plan
 │
 └── 满足完成条件 → Done

因此 Function Calling 灵活性的来源其实是：

text
Capability Discovery
        +
Dynamic Tool Selection
        +
Agent Loop
        +
Observation / Re-plan
        +
Tool Policy

而不是单纯增加 Function 数量。

15. 修改代码后必须验证

对于：

按照 Figma 修改按钮样式

不能：

text
edit_file
   ↓
Done

至少应该：

text
edit_file
   ↓
run_lint
   ↓
run_typecheck
   ↓
run_test / run_build

但这些只能证明：

代码没有明显坏掉。

不能证明：

页面视觉效果真的和 Figma 一致。

因此更完整的 Fullstack Agent 后续可以加入 Browser Runtime：

text
代码修改
   ↓
Build
   ↓
启动项目
   ↓
Browser Open
   ↓
Screenshot
   ↓
Visual Compare
   ↓
Figma Reference
   ↓
是否一致？
   │
   ├── No → Re-plan → Edit → Validate
   │
   └── Yes → Done

这就是 visual_validation Capability 的意义。

16. Capability 是否还需要分层？

当平台规模越来越大时，可以进一步采用三级模型。

一级：Domain Capability

text

design

code_execution

二级：Atomic Capability

text

├── repository_search

design
├── design_read
└── design_screenshot

code_execution
├── code_edit
└── code_validation

browser

三级：Concrete Tool

text

        ↓

        ↓

17. MCP / RAG / Code 与 Capability 的关系

这两个维度不要混淆。

例如：

text
Capability
= Agent 认为“自己能做什么”

MCP / RAG / Code
= 这个能力“通过什么方式实现”

例如：

text
design_read
        ↓
Figma MCP

knowledge_search
        ↓
RAG Runtime

repository_search
        ↓
Code Runtime

code_edit
        ↓
Code Runtime

因此平台可以保持：

text
Agent Platform
      │
      ▼
LangGraph / Agent Runtime
      │
      ▼
Capability Layer
      │
      ▼
Tool Router / Registry
      │
      ▼
Tool Runtime
 /        |        \
MCP      RAG      Code

Capability 是 Agent 视角。

MCP / RAG / Code 是 Runtime / Infrastructure 视角。

20. 最终设计原则

原则一：Capability ≠ Tool

text
Capability：我能做什么
Tool：具体怎么做

原则二：Capability Planner 不感知所有 Function

不要：

text
Capability Planner
      ↓
100 个 Function Schema

而应该：

text
Capability Planner
      ↓
10 个左右稳定 Capability
      ↓
Tool Router
      ↓
当前真正需要的少量 Function

原则三：Capability Planning 不是固定 Workflow Planning

不要机械地产生：

text
A → B → C → D → E

而应该：

text
Task
 ↓
判断可能需要的 Capability
 ↓
执行一个/多个 Tool
 ↓
Observe
 ↓
根据新信息 Re-plan

原则四：Capability 稳定，Tool 可替换

text
repository_search

底层可以从：

text
ripgrep

升级到：

text
Code Index

甚至：

text
Codex Search

Agent 上层规划无需变化。

原则五：LLM 决定意图，系统控制执行权限

text
LLM
 ↓
Tool Selection
 ↓
Policy Engine
 ↓
Tool Runtime

即：

LLM 决定“想做什么”，系统决定“允许做什么”。

原则六：Function Calling 的灵活性来自整个 Agent Runtime

最终可以概括为：

Function Calling 的灵活性，不应该靠给模型更多 Function，而应该靠 Capability Planning + Tool Discovery + Dynamic Tool Selection + Agent Loop + Tool Policy。

这套设计尤其适合 Tool 数量会不断增长的 Fullstack Agent / Agent Platform。

MCP、Function Tool 等如何统一收敛到 Tool Router / Tool Runtime

1. 核心结论

MCP Tool、Function Tool、RAG Tool、Code Runtime、Browser Runtime 等可以统一纳入同一套 Tool 架构，但需要区分“选择”和“执行”两个职责：

Tool Router 统一负责选择具体 Tool；Tool Runtime 根据 Tool 的 Provider / Executor 决定到底通过 MCP、Function、RAG、Code Runtime 还是 Browser Runtime 执行。

业务 Agent 不需要感知“这个工具是 MCP 还是 Function Calling 实现的”。它只需要知道自己拥有哪些 Capability，以及当前应该调用哪个 Tool。

text
Fullstack Agent
      ↓
Capability Planner
      ↓
Tool Registry
      ↓
Tool Router
      ↓
Tool Policy
      ↓
Tool Runtime
      │
 ┌────┼────────┬──────┬───────┐
 ↓    ↓        ↓      ↓       ↓
MCP Function   RAG    Code   Browser

2. Capability、Tool、Provider 三层不要混在一起

推荐把系统抽象成三层：

text
Capability
“Agent 能做什么？”
        ↓
Tool
“当前具体调用哪个工具？”
        ↓
Provider / Executor
“这个工具实际上怎么执行？”

例如读取 Figma 设计：

text
design_read                       ← Capability
      ↓
figma_get_design_context          ← Tool
      ↓
provider = mcp                    ← Provider
server = figma
      ↓
Figma MCP Server

代码搜索可能是：

text
repository_search                 ← Capability
      ↓
search_code                       ← Tool
      ↓
provider = function/runtime       ← Provider

5. Tool Runtime 再根据 Provider 分发

真正决定 MCP / Function / RAG / Code 的地方应该是 Tool Runtime。

伪代码：

python
async def execute(tool_call):
    tool = registry.get(tool_call.name)

    if tool.provider == "function":
        return await function_executor.execute(
            tool,
            tool_call.arguments
        )

    if tool.provider == "mcp":
        return await mcp_executor.execute(
            tool,
            tool_call.arguments
        )

    if tool.provider == "rag":
        return await rag_executor.execute(
            tool,
            tool_call.arguments
        )

    if tool.provider == "runtime":
        return await code_runtime.execute(
            tool,
            tool_call.arguments
        )

    if tool.provider == "browser":
        return await browser_runtime.execute(
            tool,
            tool_call.arguments
        )

因此职责边界为：

text
Tool Router
= 用谁？参数是什么？

Tool Policy
= 允许调用吗？

Tool Runtime
= 怎么调用？

Provider / Executor
= 具体通过什么技术执行？

9. 最终职责定义

Capability Planner

负责能力级的粗粒度规划和缩小搜索空间。

回答：

完成任务需要哪些能力？

Tool Registry

负责维护 Capability → Tool，以及 Tool → Provider / Schema / Risk 等 Metadata。

回答：

这些能力下面有哪些可用工具？

Tool Router

基于 Task、Current Agent State、Capability Scope 和 Candidate Tools，定位当前最合适的具体 Tool，并生成调用参数。

回答：

现在具体调用哪个 Tool？

Tool Policy

对 Tool Call 做权限、风险、资源和安全校验。

回答：

这个 Tool Call 是否允许执行？

Tool Runtime

屏蔽 Tool 的底层实现差异，根据 Provider 将调用分发给 MCP、Function、RAG、Code、Browser 等 Executor。

回答：

这个 Tool 到底怎么执行？

10. 一句话总结

Capability Planner 屏蔽“具体有哪些工具”，Tool Router 屏蔽“当前应该选哪个工具”，Tool Runtime 屏蔽“这个工具到底通过 MCP、Function、RAG、Code 还是 Browser 实现”。

因此对于 Fullstack Agent / Agent Platform，上层 Agent 应该面向 Capability 和统一 Tool 抽象编程，而不是直接绑定 MCP、Function Calling 或某个具体工具提供方。
