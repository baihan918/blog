10项关键纠错
RAG 不是训练模型它是在回答前，把外部证据临时放进模型上下文。

01 · THE MENTAL MODEL

先分清两条流水线：离线建库，在线回答

Notebook 为了演示方便，常在一个函数里从 PDF 一路跑到答案。真实系统必须把“文档发生变化时做的事”和“每次用户提问时做的事”拆开。

离线：文档更新时运行在线：每次提问时运行

离线建库：把资料整理成“书架索引”

读取 PDF、网页或数据库，清洗后切成小块，为每块生成 Embedding，并连同来源、页码、版本写入向量库。

触发时机：文档新增、更新、删除，或 Embedding 模型更换。

在线查询：带着问题去“书架找证据”

理解问题，必要时改写或分解；召回候选证据，过滤与重排，然后把证据和问题交给 LLM。

触发时机：每一次用户提问。
一句话：RAG = Retrieval（找证据）+ Augmented Context（把证据放进上下文）+ Generation（根据证据回答）。向量数据库只是 Retrieval 的一种实现，不等于整个 RAG。

03 · DOCUMENT PREPARATION

切块不是“把字符串切短”，而是在控制证据颗粒度

块太小，事实被拆散；块太大，主题被稀释且浪费 token。没有一个永远正确的 chunk size，应该用真实问答集评估召回质量。

固定长度切块

实现简单、速度快，适合格式稳定的文本；缺点是可能在句子或主题中间切断。

语义切块

在句子语义变化明显处断开，更容易保留主题；成本更高，阈值也需要评估。

命题切块

把复合段落改写成独立事实命题，适合精确事实检索；要防止生成模型改写时引入新事实。

策略真正解决的问题适合场景主要风险
标题 / 上下文增强单独的块离开原章节后语义不完整长报告、层级文档增强文本不能冒充原文引用
文档问题增强用户问题与原文措辞差异太大FAQ、产品知识库合成问题需要和原文绑定
分层索引既要先定位主题，又要拿到细节长文档、书籍、规范摘要层只能导航，最终证据仍应回到原文
多模态处理关键证据藏在图片、图表、扫描页财报、论文、说明书图片描述是模型生成物，需要保留原图引用
先验收解析，再讨论检索。如果 PDF 读出来是 %PDF-1.7、交叉引用表或乱码，说明 Reader 没有真正解析 PDF；此时调 chunk size、top-k、Prompt 都没有意义。
04 · QUERY UNDERSTANDING + ROUTING

意图识别发生在检索前：决定接下来走哪条路

意图识别不是为了给问题贴标签，而是为了改变动作：是否检索、查哪个知识源、要不要分解、选语义还是关键词、是否需要最新数据或计算工具。

上面的路由器是教学规则，不是生产分类器。生产系统应使用结构化输出（枚举 + 校验）、置信度和兜底策略；低置信度时可以澄清，而不是硬猜。
一个更可靠的分类输出应该长什么样？
structured_intent.py同一套中文枚举贯穿全流程
from enum import Enum
from pydantic import BaseModel, Field

class QueryIntent(str, Enum):
    FACTUAL = "事实"
    ANALYTICAL = "分析"
    GLOBAL_SUMMARY = "全局总结"
    CONTEXTUAL = "依赖上下文"
    FRESH = "时效信息"

class RouteDecision(BaseModel):
    intent: QueryIntent
    needs_retrieval: bool
    needs_clarification: bool = False
    confidence: float = Field(ge=0, le=1)

decision = classify_once(query)       # 只分类一次
docs = retrieve(query, decision)      # 把结果显式传下去
05 · TECHNIQUE MAP

每种增强技术都只是在修一段链路

遇到效果差，先定位是哪一阶段失效，再选择技术。盲目同时叠加查询重写、HyDE、混合检索、重排和压缩，往往只会增加成本并让问题更难排查。

查询重写

把口语、省略和歧义改写成更适合知识库检索的表达。

适合：原问题表达不完整

Step-back

先提出更高层问题，找背景知识，再回答具体问题。

适合：需要原理或背景的复杂问题

子查询分解

把多跳问题拆成若干可独立检索的小问题，再合并证据。

适合：比较、因果、多条件问题

HyDE

先生成“可能答案长什么样”的假设文档，用它的向量去找真实文档。

适合：短问题和文档措辞差距大

混合检索

向量检索负责语义相近，BM25 负责精确词、编号和专有名词。

适合：既有自然语言又有精确标识

分层检索

先在摘要层定位主题，再限定范围检索原文细节。

适合：文档长、层级明确

Graph RAG

用实体、关系和社区结构找跨片段、多跳关联。

适合：关系推理，而非所有知识库

Rerank

对较大的候选集做更精细的“问题—文档”相关性排序。

适合：召回率尚可，前几名不够准

RSE 段落重构

把相邻高价值块重新拼成连续段落，恢复跨块上下文。

适合：答案跨越多个相邻块

上下文压缩

从候选证据中抽取与当前问题有关的句子，减少噪声和 token。

适合：top-k 较大、内容重复

Self-RAG 思路

决定是否检索，并检查证据相关性、答案支持度和实用性。

适合：需要动态检索和自检

CRAG

评估初始检索质量；证据不足时改写查询、换知识源或网络搜索。

适合：知识库可能缺失或过时
Rerank 是候选上下文进入 Prompt 前的质量门，不是最终答案质量门。它能提高证据排序，但不能保证最终答案忠实、完整，也不能代替引用校验与答案评估。
06 · CONTROL LOOPS

高级 RAG 的共同点：不再“一次检索、一次生成就结束”

Self-RAG、CRAG、反馈回路和强化学习都在引入“观察—判断—调整”。区别在于：谁做判断、调整什么，以及是否真的训练了一个可学习策略。

Observe · 观察检索分数、证据内容、答案、用户反馈、时效性。
→
Judge · 判断相关吗？支持答案吗？信息够吗？需要换知识源吗？
→
Act · 调整重写查询、扩充或过滤上下文、重新检索、拒答或升级人工。

Self-RAG

原论文方法把“是否检索、证据是否相关、回答是否被支持”等反思能力训练进模型，并使用特殊 reflection tokens。Notebook 实现的是受 Self-RAG 启发的多次 LLM 判断流程，适合学习控制思想，但不是论文级复现。

CRAG

核心是给检索结果做质量分级：可信则使用，不可信则纠正或换外部来源，模糊则组合。外部网页不是天然可信，仍需来源筛选、时间戳和引用。

反馈闭环

用户评分可以作为 rerank 特征、训练数据候选或评估集，但不能把未经审核的模型回答直接当事实写回知识库，否则错误会自我强化。

强化学习

真正的 RL 需要环境、状态、动作、奖励和由奖励更新的策略。只有 epsilon-greedy 启发式和“记录动作”的字典，还不等于策略网络被训练。

生产建议：先用确定性规则 + 结构化分类 + 离线评估建立稳定基线；只有当动作选择问题明确、奖励可靠、数据量足够时，再考虑强化学习。
07 · CORRECTIONS

原 Notebook 中需要特别纠正的 10 个点

以下不是吹毛求疵：其中几项会让代码永远走默认分支，或让实验名称比实际实现更“高级”。学习时应该区分“概念演示”和“可正确运行的实现”。

运行错误

自适应检索中英文标签不一致

原实现classify_query() 返回“事实性”，路由却判断 "Factual"，所以总会进入默认事实检索。
正确做法用同一套 Enum 或中文常量贯穿分类与路由，并对模型输出做结构化校验。
成本错误

同一个问题被重复分类

原实现完整管道先分类一次，adaptive_retrieval() 内部又分类一次；评估函数还会继续重复。
正确做法入口只分类一次，将 RouteDecision 显式传给检索器和生成器。
运行错误

自适应 RAG 的相关性判断也不匹配

原实现评估器返回“相关 / 完全支持”，代码却判断 "relevant" 和 "fully supported"，导致相关文档被丢弃、支持分恒为 0。
正确做法统一语言枚举，或让模型直接返回 JSON / Pydantic 结构。
概念校准

Notebook 的 Self-RAG 不是原论文复现

容易误解把几个独立 LLM Judge 调用命名为“完整 Self-RAG”。
正确理解这是 Self-RAG-inspired inference pipeline；原方法涉及反思 token 和专门训练。
概念校准

Graph RAG 不只是“块相似图”

原示例边界节点仍是文本块，按共享概念和向量相似度连边；遍历深度还使用全局访问数量，不能代表真实层深。
正确理解这是图增强检索 Demo。完整 GraphRAG 通常包含实体关系抽取、社区、社区摘要和多层查询。
概念校准

“策略网络”并没有真正学习

原实现policy_network() 是启发式 epsilon-greedy；update_policy() 只是把动作和奖励记入字典。
正确理解应称为 RL 交互骨架或 bandit 风格 Demo，不能说已训练了神经策略网络。
架构错误

不要每次请求都重新解析 PDF 和建库

Notebook 为演示方便很多完整管道在每个 query 内调用 process_document(pdf_path)。
正确做法离线持久化索引；在线只向量化 query、检索、重排和生成。
数据风险

用户好评不能自动变成事实

原反馈示例把高分“问题 + 模型回答”作为新文档写进向量库，容易把幻觉固化并放大。
正确做法进入候选区，经过来源核验、去重、权限与人工审核后再发布；原始资料仍是事实来源。
概念校准

不要保存和压缩隐藏的 Chain of Thought

原说明建议在交互中压缩“历史推理轨迹”。
正确做法保存可审计的任务状态、工具结果、证据、决策摘要和最终结论，不依赖模型隐藏思维链。
证据风险

HyDE 假设文档不能当证据

容易误解假设文档写得像“权威来源”，但内容本质上是模型猜测。
正确做法它只用于生成检索向量；最终回答必须基于真正召回的原文，并保留来源。
08 · CORRECT REFERENCE

把正确边界写进一个最小参考实现

下面是框架无关的 Python 骨架，重点不在某个 SDK，而在职责分离：索引持久化、分类只做一次、候选召回与重排分开、回答只使用真实证据。

离线：构建并持久化索引
build_index.py文档变化时执行
def build_index(source_paths):
    documents = reader.load(source_paths)
    assert_parsing_quality(documents)          # 先抽样检查正文、页码、表格

    nodes = splitter.split(documents)
    nodes = add_metadata(
        nodes,
        fields=["source_path", "page", "version", "updated_at"],
    )

    vectors = embedder.embed_documents([n.text for n in nodes])
    vector_store.upsert(nodes, vectors)
    vector_store.persist("./storage")   # StorageContext 本身不等于已落盘
在线：分类一次，检索、重排、生成
answer.py每次用户提问执行
def answer(query, conversation=None):
    decision = classify_once(query, conversation)    # 结构化 RouteDecision

    if decision.needs_clarification:
        return ask_for_clarification(decision)

    rewritten = transform_query(query, decision)
    candidates = hybrid_retrieve(                   # 扩召回，例如 top 30
        rewritten,
        filters=decision.metadata_filters,
        top_k=30,
    )
    evidence = reranker.rank(query, candidates)[:6]

    if not enough_evidence(evidence):
        return insufficient_answer_with_sources(evidence)

    result = generator.answer(
        question=query,
        evidence=evidence,                           # 不把 HyDE 文本当证据
        require_citations=True,
    )
    return verify_and_format(result, evidence)

embed_documents()

通常用于批量文档；可能带适合文档侧的前缀或批处理参数。

embed_query()

用于用户问题。必须与建库模型处于同一向量空间，但某些模型的 query/document 编码方式不同。

Embedding 维度必须匹配向量索引。建库与查询必须使用同一模型和同一归一化规则；更换模型通常意味着重建索引，而不是只改一个配置字符串。
09 · DEBUG + EVALUATION

RAG 答错时，按数据流从前往后查

不要一上来改 Prompt。先确认事实有没有进入系统，再确认它是否被召回，最后才看模型有没有忠实使用证据。

01
解析正确吗？抽样打印 PDF 正文、表格、图片描述、页码和文件名。
reader output
02
切块保住事实了吗？检查答案是否跨切口、标题是否丢失、metadata 是否跟随 Node。
nodes[:5]
03
Retriever 找到了吗？直接查看 top-k 的正文、score、来源，不调用生成模型。
retrieve(query)
04
Rerank 排对了吗？看正确证据是否在候选集中，以及重排后名次如何变化。
candidate → reranked
05
答案被证据支持吗？逐条核对事实、数值和引用；证据不足时应该明确拒答。
faithfulness
评估层应该测什么常用指标常见误区
解析 / 切块关键事实是否进入 Node，来源是否完整抽样通过率、表格/图片覆盖率只看代码没报错
召回正确证据是否进入候选集Recall@k、MRR、nDCG只看向量相似度分数
重排正确证据是否排到 Prompt 可容纳的位置Precision@k、nDCG@k把重排当最终答案校验
生成答案是否正确、完整、忠于证据Faithfulness、Answer correctness、引用准确率只用同一个 LLM 自评一次
系统成本、延迟、稳定性和新鲜度P95 延迟、token、失败率、索引时效只优化回答观感
评估集要来自真实业务问题。至少记录问题、标准证据、参考答案、不能回答的反例，以及版本/时间。否则调参得到的“提升”很可能只是对几个示例过拟合。

11 · GLOSSARY

最后用一张术语表收口

Document
Reader 读取外部资料后的统一对象，包含正文和文件级 metadata。
Node / Chunk
Document 切分后的可检索单元；应保留来源、页码和父级关系。
Embedding
把文本映射为向量；相近向量代表语义上可能相关，不代表事实一定正确。
Vector Store
保存并搜索向量的组件；只是检索基础设施，不负责生成答案。
BM25
基于词频的关键词检索，擅长专有名词、编号和精确措辞。
Hybrid Retrieval
融合语义检索和关键词检索，常用加权分数或 Reciprocal Rank Fusion。
Retriever
召回候选证据，目标偏向“不漏”；通常先取较大的 top-k。
Reranker
对候选证据做更精细排序，目标偏向“把最准的放前面”。
Context Compression
检索后、生成前，抽取或压缩与问题有关的证据，减少噪声。
HyDE
用假设文档改善检索表达；假设内容不能作为最终事实依据。
Self-RAG
带检索决策与反思信号的训练/推理方法；不能泛指所有 LLM 自检流程。
CRAG
检测检索质量并在证据不足时纠正、换源或扩展检索。
Graph RAG
利用实体、关系、社区或图遍历完成关联与多跳检索。
Faithfulness
答案中的事实是否能被提供的证据直接支持。
最终心智模型：先保证“资料读对了”，再保证“证据找到了”，然后保证“证据排在前面”，最后保证“答案没有超出证据”。高级 RAG 只是让这条链路可以判断、纠正和迭代。
