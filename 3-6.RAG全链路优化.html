02 · 入库优化：文档预处理的边界

目标不是把文本改得“越短越好”，而是把解析结果变得稳定、干净、结构清楚，同时保留可影响答案的语义。

输入：解析后的结构化文档

  • 正文、标题、段落、表格与列表
  • 页码、坐标、文件名、章节层级
  • 可能包含 OCR 错误、页眉页脚和乱码
→

输出：干净但语义完整的 Document

  • 统一编码与稳定的文本格式
  • 保留标题、表格、列表等结构线索
  • 携带来源和质量标记，准备进入切块
边界提醒：文件解析解决“读出来”，预处理解决“清理好”，切块解决“怎样分段”，Embedding / Analyzer 解决“怎样建立检索表示”。实际框架可能把这些步骤封装在一起，但排查时仍应分层。

03 · 入库优化：文档预处理步骤

以下顺序适合作为工程流水线。每一步都应尽量可配置、可回放，并保留原始资料作为事实源。

格式与编码统一

识别 UTF-8、GBK 等编码，统一换行、全半角和 Unicode 表示；原始文件不要覆盖。

解析质量检查

检查空文本、乱码比例、OCR 置信度、页数和表格数量。PDF 出现 %PDF 内容通常代表解析器用错。

版面噪声清理

处理重复页眉页脚、页码、连续空白、断行和不可见字符；避免用宽泛正则误删正文。

结构恢复与保留

保留标题层级、段落边界、列表序号、表格行列以及图片说明，为结构化切块提供信号。

内容标准化

根据检索需求做大小写、全半角、繁简转换等标准化；产品型号、金额、日期和否定词不能被破坏。

重复与模板识别

识别完全重复、近重复内容以及批量文档模板，减少同一证据挤占 Top-K，但保留版本关系。

安全与权限标记

识别敏感信息、注入性文本和访问权限。是否脱敏取决于业务规则，权限信息必须进入元数据。

生成可追踪中间结果

输出 clean_text、结构块、source、page、version、status 和质量告警，便于重建索引与回源。

哪些“清洗”不要默认做？

通常可以做

  • 清除乱码、控制字符和重复空白
  • 识别并去除重复页眉页脚
  • 统一编码、全半角和换行
  • 保留原文的同时建立规范化字段
  • 记录解析失败和低质量页面

不要默认做

  • 向量化前删除停用词
  • 直接用同义词覆盖原文
  • 删除“不、未、之前、之后”等词
  • 把分词结果交给 Embedding 代替原句
  • 只保存向量、不保留原始文档与来源
原文
本产品不支持七天无理由退款，质量问题除外。
→
错误的激进过滤

“不”被删除后，核心结论反转。

⇢

Dense / Embedding 分支

  • 输入自然、完整的文本
  • 通常不删除停用词
  • 通常不做同义词替换
  • 不需要预先中文分词

Sparse / BM25 分支

  • Analyzer 做分词与规范化
  • 领域词加入自定义词典
  • 同义词优先做低权重扩展
  • 停用词仅在评测证明有益时过滤
为什么 BM25 不怕普通高频词？ BM25 已通过 IDF 降低全库高频词权重，通过词频饱和避免重复词无限加分，并用文档长度归一化修正长文档优势。因此停用词过滤不是默认必选项。

04 · 入库优化：中文分词器与词典

分词主要服务关键词检索，不服务 Embedding。真实项目通常跟随检索基础设施选择，优先保证文档侧与查询侧规则一致。

技术栈常见选择适合场景建议
Elasticsearch / OpenSearchIK Analyzer中文全文检索、企业知识库文档侧可从 ik_max_word 起步，查询侧按评测选择 ik_smart 或同模式。
Milvus 内置 BM25chinese / jiebaDense + Sparse 混合 RAG直接使用 Milvus Analyzer，避免应用层重复分词；创建 Collection 前确认配置。
Python 本地 DemoJieba教学、PoC、小型 BM25使用搜索模式提高召回，并加载小而准的领域词典。
复杂中文 NLPHanLP 等还需要词性、实体、句法信息能力更强但成本更高，不要只为普通 BM25 过度引入。
ik_max_word 到底是什么？

它是 IK Analyzer 的细粒度分词模式，不是独立产品。它会尽可能输出长词及可识别的短词，偏向提高召回；ik_smart 粒度更粗，偏向减少噪声。两者都需要用真实查询验证，不能只凭名称决定。

自定义分词词典应该放什么？

优先加入业务专有名词、产品型号、公司名、中英文混合词和容易被切错的固定短语。不要一开始堆一个巨型词库，应从查询日志和召回失败样本逐步补词。

同义词应该替换还是扩展？

优先保留原查询并扩展，例如“退钱 OR 退款 OR 退费”，而不是覆盖原文。原词权重最高，扩展词降低权重；Embedding 分支仍使用原始自然语言。

05 · RAG 全链路的当前代码映射

本项目当前不是 Milvus，而是“自定义解析/分词 + Embedding + Elasticsearch 混合检索”。下面是从入库到查询的真实代码入口。

1
core/file_parse.py
调用 manual.chunk() 解析文件，生成 Chunk；为每个 Chunk 生成 ID、文档元数据、分词字段和向量，然后写入 Elasticsearch。
2
rag/app/manual.py
PDF 走 OCR、版面分析、表格识别与文本合并；DOCX 保留问题层级和表格；随后按标题层级与 token 数合并为 Chunk。
3
rag/nlp/rag_tokenizer.py
项目自带 Huqie 风格词典分词：全半角、繁简和小写标准化，前后向切分、细粒度切分，并支持加载用户词典；它不是 IK。
4
rag/nlp/model.py
通过 generate_embedding() 为 Chunk 和用户问题生成向量，向量字段名包含实际维度。
5
rag/nlp/query.py
对查询做标准化、分词、词权重、细粒度展开和低权重同义词扩展，构建全文检索表达式。
6
rag/nlp/search_v2.py
同时生成全文 Match 与 Dense Match，在 Elasticsearch 侧融合候选，再按关键词/向量相似度或重排模型得到最终 Chunk。

06 · 入库链路的预处理验收清单

不要只检查“程序有没有报错”，而要抽样验证从解析文本到检索字段的真实形状。

检查对象应该看到什么常见失败信号
解析文本正文可读，标题、表格和段落基本保留%PDF、乱码、整页为空、顺序错乱
语义完整性否定、数字、单位、时间、产品型号仍然存在“不支持”变成“支持”，金额或单位丢失
重复内容页眉页脚不反复占据 ChunkTop-K 被相同模板或重复页面占满
结构信号标题层级、页码、表格和来源可追踪只能看到一段文本，无法定位原文
关键词字段领域词切分正确，文档与查询规则一致产品名被拆碎，查询词和索引词完全错位
向量字段维度一致，输入是完整 Chunk 原文维度不匹配，或把空格分词串送入 Embedding
回归评测真实问题的 Recall@K、MRR 和答案准确率可比较仅凭肉眼觉得“清洗后更干净”

07 · 查询链路优化：如何提升首字速度

TTFT（Time To First Token）不只是大模型的速度，而是从用户发出问题，到界面收到第一个有效 token 之间的全链路时间。优化前必须先知道时间花在了哪里。

TTFT ≈ 网关 / 鉴权+ 查询改写+ Embedding+ 检索 / Rerank+ 上下文组装+ 模型排队 / Prefill
常见大头 01查询改写额外串行调一次 LLM，可能直接多出数百毫秒。
通常较快Embedding小模型、同地域、连接复用和缓存能进一步降低延迟。
通常较快ANN 检索先查过滤索引、跨区访问、冷启动和连接池。
可能昂贵Rerank延迟随候选数增长，不应无条件重排大量 Chunk。
容易被忽略Prompt 长度上下文越长，生成前的 Prefill 通常越慢。
常见大头 02LLM 首 token受模型规模、服务排队、网络和推理引擎影响。

1. 先分段测量，不要凭感觉换组件

分别记录查询改写、Embedding、检索、Rerank、Prompt 组装和 LLM 首 token 的耗时。一定要看 P50 和 P95，同时记录最终输入模型的 token 数。

from time import perf_counter

t0 = perf_counter()

# retrieve() 只负责拿候选节点，适合作为检索 / 生成的分界点
nodes = retriever.retrieve(query)
t_retrieved = perf_counter()

stream = llm.stream_chat(build_messages(query, nodes))
t_llm_requested = perf_counter()
first_token_at = None

for chunk in stream:
    text = chunk.delta or ""
    if text and first_token_at is None:
        first_token_at = perf_counter()
        print({
            "retrieval_ms": (t_retrieved - t0) * 1000,
            "llm_ttft_ms": (first_token_at - t_llm_requested) * 1000,
            "end_to_end_ttft_ms": (first_token_at - t0) * 1000,
        })
    render(text)
阶段耗时 rewrite / embedding / retrieval / rerank 模型耗时 queue / network / prefill 输入规模 prompt_tokens / chunk_count 分位数 P50 / P95 / timeout rate
不要只记录整个请求耗时：如果 LLM 首 token 用了 1100ms，向量检索只用了 35ms，优先更换向量库几乎不会改善用户等待。

2. 按收益排序的优化动作

1

移除串行 LLM 调用

简单问题直接检索；查询改写用规则或小模型；只在召回置信度低时做二次改写。HyDE、意图识别和路由也不应默认串行。

2

减少 Prompt token

降低最终 Top-K，去掉重复与相邻 Chunk，只传命中的局部段落，历史对话使用摘要，移除重复指令和冗长 metadata。

3

控制检索与 Rerank

Embedding 使用小模型和缓存；检索使用 ANN 索引；先召回 10～20 条，有条件地 Rerank，最终只选 3～5 条进入 Prompt。

4

并行独立任务

Dense 与 BM25、多个知识源、可并行的权限与元数据查询同时执行。并行后总耗时接近最慢分支，而不是所有分支之和。

5

优化模型与网络

选首字快的模型，让应用、Embedding、向量库和 LLM 尽量同地域；保持 HTTP 长连接与连接池，预热 Serverless 实例，对固定前缀使用 Prompt Cache。

6

立即流式输出

收到第一个有效 chunk 后立即渲染，不等完整答案。但流式主要改善用户感知，不会消除流式开始前的检索、Rerank 和 Prefill。

3. 推荐的低延迟架构

快速判断
→
用本地规则判断是否需要 RAG；不固定调用一个 LLM 进行路由。
并行召回
→
查询 Embedding 使用缓存；Dense 与 BM25 并行；多知识源并行，然后统一去重与融合。
质量门禁
→
候选结果模糊或冲突时再启用轻量 Rerank，最终保留 3～5 个证据 Chunk。
紧凑上下文
→
在 token budget 内优先保留高相关、不重复、可引用的局部原文，避免把整篇文档塞进 Prompt。
流式生成
→
调用同地域的低延迟模型，复用连接并立即流式渲染；引用整理不应无条件阻塞首字。
如果只先做三件事：① 给每个阶段加耗时埋点；② 去掉生成前不必要的串行 LLM 调用；③ 减少最终进入模型的上下文 token。这三项通常比“先换向量库”更能改善首字速度。
