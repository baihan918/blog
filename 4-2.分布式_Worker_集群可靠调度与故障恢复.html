1. 从线程池到分布式

当前项目通过本机 ThreadPoolExecutor 调用 Worker：

single process
future = executor.submit(worker.execute, subtask)
result = future.result()

这里的 Future、Worker 状态和结果都依附于当前 Python 进程。分布式以后，Orchestrator 不再直接调用某个 Worker，而是发布一份可持久化、可重试的任务消息：

distributed
task_queue.publish({
    "event_type": "subtask.ready",
    "research_id": "research_123",
    "subtask_id": "subtask_001",
    "attempt": 1,
    "payload": {...}
})
分布式的本质不是把同一个线程池放大，而是让执行进程可以消失，同时任务仍能从持久化状态中恢复。

2. 五个基础组件

可靠系统至少需要下面五类角色，每一类只承担一种主要责任。

Frontend提交与观察
Orchestrator计划与推进
Queue可靠传递
Worker Cluster执行与心跳
DB / Object Store权威状态与大结果
组件负责什么不应该负责什么
Frontend提交任务、显示进度、重新连接持有任务生命期
Orchestrator拆任务、推进状态、聚合结果依赖某个实例的本地内存
Queue可靠传递、重投与削峰作为最终权威状态库
Worker执行一个 SubTask 及其内部 OODA决定全局报告何时完成
Database保存任务、子任务、事件和执行版本存放无限膨胀的大段原始证据

3. 子任务为什么需要落库

耗时、异步或跨机器执行的 SubTask 应该落库。数据库中的记录不是日志副本，而是系统判断“下一步做什么”的权威事实。

父任务：research_tasks

schema
id                       research_123
original_task            用户的原始研究问题
status                   researching
stage                    initial_research
expected_subtasks        4
completed_subtasks       3
iteration                1
quality_score            null
final_report_location    null
error_message            null
created_at               2026-08-15T12:00:00
updated_at               2026-08-15T12:03:00
version                  7

父任务可使用 pending → planning → researching → synthesizing → iterating → completed 的主状态链，并补充 failed、cancelled 等终止状态。

子任务：research_subtasks

schema
id                  subtask_001

phase               initial

result_location     null
error_message       null
created_at          2026-08-15T12:00:01
updated_at          2026-08-15T12:00:40

事件表：research_events

replayable progress event
id             1024

subtask_id     subtask_001

搜索证据、OODA 轨迹和最终报告可能较大，可以进入对象存储；数据库只保留状态、索引、校验值和结果地址。

4. 事件如何找到正确任务

你的理解方向是对的：先监听某类事件，再根据标识找到需要更新的任务。但生产系统不能只依赖 subtask_id。

event envelope
{
  "event_id": "event_789",
  "event_type": "subtask.completed",
  "research_id": "research_123",
  "subtask_id": "subtask_001",
  "attempt": 2,
  "worker_id": "worker_8",
  "result_location": "results/subtask_001.json"
}
字段作用
event_type决定交给哪个事件处理器
research_id加载整条研究工作流状态
subtask_id定位需要更新的具体执行单元
attempt识别旧 Worker 的迟到结果
event_id判断该事件是否已经处理过
event handler
def handle_subtask_completed(event):
    if processed(event.event_id):
        return

    state = load_research(event.research_id)
    subtask = load_subtask(event.research_id, event.subtask_id)

    if event.attempt != subtask.current_attempt:
        return  # 丢弃旧执行的迟到事件

    mark_completed(subtask, event.result_location)

    if all_subtasks_completed(event.research_id):
        publish("research.ready_to_synthesize", event.research_id)

5. 共享队列里的过滤陷阱

危险：实例拿到后再过滤

Orchestrator B 从竞争队列拿到了属于 A 的事件，发现不是自己的就丢弃。A 将永远收不到这个事件。

推荐：统一无状态处理器

任意实例都能消费事件，并根据 research_id 从数据库加载状态、幂等更新和推进工作流。

在 Kafka 一类分区系统中，可以使用 research_id 作为消息 Key，让同一研究任务的事件进入同一分区：

partition routing
producer.send(
    topic="subtask-events",
    key=research_id,
    value=event,
)

即使按 Key 路由，消费者仍应从数据库读取状态，不能假设某个进程一直拥有某个 research_id。

6. 前端崩溃为什么不应影响任务

前端只负责提交和观察，不能成为任务的宿主。正确接口在持久化任务并可靠入队后立即返回：

http
POST /research
→ 数据库创建 research_123
→ Outbox 记录 subtask.ready
→ HTTP 202 Accepted

{
  "task_id": "research_123",
  "status": "pending"
}

页面关闭、刷新或网络断开后，队列和 Worker 仍然继续。前端重新打开只需要查询相同任务：

reconnect
GET /research/research_123

GET /research/research_123/events?after=1024
Last-Event-ID: 1024

恢复方式一：轮询

polling
setInterval(async () => {
  const task = await fetch("/research/research_123");
  renderTask(await task.json());
}, 2000);

恢复方式二：SSE 断点续传

前端保存最后收到的事件 ID。重连时携带 Last-Event-ID: 1024 或查询 ?after=1024，后端从事件表补回缺失进度：

missed events
1025  subtask.completed
1026  synthesis.started
1027  quality.checked
SSE 是进度展示通道，不是任务执行通道。SSE 断开只代表“看不到直播”，不代表任务应该取消。

7. Worker 崩溃如何由其他节点接管

Worker 领取任务后不应该永久占有它，而是获得一个有期限的执行租约。

lease lifecycle
12:00:00  Worker 8 claim，lease 到 12:01:00
12:00:20  心跳续期，lease 到 12:01:20
12:00:40  心跳续期，lease 到 12:01:40
12:00:45  Worker 8 崩溃
12:01:40  lease 过期
12:01:41  subtask 重新进入 pending
12:01:42  Worker 3 以 attempt=2 接管

恢复器还应定期扫描卡住的状态：租约已过期的 running 子任务、全部子任务完成但未汇总的父任务、已经生成报告但仍未标记 completed 的任务。

8. 幂等、重复投递和迟到事件

可靠队列通常提供“至少投递一次”。Worker 可能已经写入结果，但在 ACK 之前崩溃，于是同一消息再次投递。

idempotency
idempotency_key = research_id + ":" + subtask_id + ":" + attempt

INSERT INTO worker_results (...)
ON CONFLICT (idempotency_key)
DO NOTHING;

事件处理同样要幂等。如果 subtask.completed 被消费两次，不能把 completed_subtasks 加两次。旧 attempt 的迟到结果也不能覆盖新 Worker 的结果。

9. 为什么需要 Transactional Outbox

“写数据库”和“发队列消息”是两个系统，任何先后顺序都存在崩溃窗口：

failure window
1. 数据库创建 subtask_001
2. 进程准备 publish
3. 进程崩溃

结果：数据库有 pending 子任务，队列却没有消息

Outbox 将业务变更和待发布事件放进同一个数据库事务：

transactional outbox
BEGIN;
INSERT INTO research_subtasks (...);
INSERT INTO outbox_events (event_type, payload, published=false);
COMMIT;

Outbox Publisher:
  扫描 published=false
  → 发布到队列
  → 标记 published=true

Publisher 即使重启也能继续扫描；消息即使重复发布，也由消费端幂等消化。

10. OODA 状态保存到什么粒度

不需要保存模型隐藏推理，也不需要把每个局部变量落库。建议在每轮 Act 完成后保存可恢复检查点：

ooda checkpoint
{
  "research_id": "research_123",
  "subtask_id": "subtask_001",
  "attempt": 2,
  "current_cycle": 3,
  "queries_used": 5,
  "query_history": ["...", "..."],
  "evidence_location": "evidence/subtask_001/cycle-3.json",
  "last_action": "search",
  "next_state": "orient"
}
应该保存无需保存
已执行查询、预算、证据、工具结果模型隐藏推理过程
当前周期、最后动作、下一状态可从证据重新计算的临时字符串
终止原因、结果地址、校验值每一个函数内局部变量

第一版最适合的粒度是：一个队列任务对应一个完整研究 SubTask，Worker 内部执行整个 OODA，并在每轮 Act 后保存检查点。

12. 当前项目怎么逐步演进

当前项目的 TaskManager 使用进程内字典，研究任务通过本地线程池运行。前端关闭时，只要 API 进程仍在，任务通常还能继续；但 API 重启会丢失任务状态。

故障或部署形态当前项目的实际结果
用户关闭页面只要后端 Python 进程仍在，任务通常继续运行
SSE 或网络断开任务继续，但前端暂时收不到实时进度
API 服务重启TaskManager.tasks 是内存字典，任务状态全部丢失
Python 进程崩溃进程内线程池和正在执行的 Worker 一起消失
多实例部署每个实例各自保存任务，查询请求落到别的实例时可能找不到
Worker 卡死当前缺少租约、心跳和自动接管机制，可能永久停在执行中

因此当前实现只能保证前端断开时任务大概率继续，不能保证后端进程故障后任务继续。

  1. 第一步：把 ResearchState、父任务和 SubTask 持久化，前端只持有 task_id。
  2. 第二步：增加事件表与 SSE 断点续传，让页面刷新后恢复进度。
  3. 第三步：用 Outbox + 持久化队列替换 executor.submit()。
  4. 第四步：把 SearchWorker 做成独立消费者，增加 lease、heartbeat、retry 和幂等。
  5. 第五步：把 Orchestrator 改成由事件驱动、可从数据库恢复的状态机。
  6. 第六步：增加 Reconciler，主动修复租约过期和停滞工作流。
最终目标：Frontend 只观察；Database 保存事实；Queue 可靠传递；Worker 可以随时重启；Orchestrator 可以由任何实例继续推进。

13. Worker 集群具体如何消费任务

Orchestrator 发布任务后，不指定某一台机器。所有同类型 Worker 运行相同的消费者程序，从共享队列竞争领取任务。常见承载方式包括 Redis、RabbitMQ、Kafka、云厂商消息队列，以及 Celery、RQ 等任务框架。

worker consumer loop
while True:
    task = task_queue.consume()

    try:
        result = execute_task(task)
        save_result(result)
        task_queue.ack(task)
    except Exception:
        task_queue.retry_or_reject(task)

假设集群有 10 个 Worker，实际分配可能是下面这样；Orchestrator 只关心任务状态，不关心节点编号：

dynamic assignment
task_1 → Worker 3
task_2 → Worker 8
task_3 → Worker 1
task_4 → Worker 6

这些 Worker 可以位于不同进程、容器或服务器。结果本身也应独立建模：

WorkerResult
{
  "subtask_id": "task_1",
  "success": true,
  "result_location": "object-storage/results/task_1.json"
}

存储职责必须分清：数据库保存任务状态和索引，对象存储保存大型搜索结果、报告与日志，队列保存待传递的消息但不作为最终事实来源。

14. Orchestrator 怎么判断所有子任务完成

讨论中给出了两种常见办法，它们不是互斥关系。

方式一：轮询数据库

poll database
while True:
    completed = count_completed_subtasks(research_id)
    if completed == expected:
        break
    time.sleep(1)

优点是逻辑简单、数据库事实明确；缺点是会产生持续轮询压力，完成后的推进也有一个轮询间隔。

方式二：完成事件

event-driven progress
task_1.completed → 1 / 4
task_3.completed → 2 / 4
task_2.completed → 3 / 4
task_4.completed → 4 / 4 → 开始汇总

生产系统通常组合使用：事件负责及时推进，数据库负责最终校验和故障恢复。事件丢失或处理器重启时，Reconciler 仍能从数据库发现“4/4 已完成但尚未汇总”的任务。

15. OODA 的调度粒度与补充研究

OODA 可以有两种队列粒度。当前 Deep Research 项目的第一版更适合粗粒度方案。

方案一个队列任务代表什么取舍
粗粒度一个完整 SubTask，Worker 内部执行 Observe → Orient → Decide → Act实现简单、消息少、延迟低，适合当前项目
细粒度Observe、Orient、Decide、Act 分别成为任务恢复更精细，但状态管理、消息数量和协调成本显著增加

只有单轮特别长、不同步骤依赖不同机器类型，或必须在步骤级暂停与迁移时，才值得把 OODA 拆细。粗粒度也要在每轮 Act 后保存检查点，不能只在整个 SubTask 结束时保存。

质量不足时如何再次调度

supplementary research
初始 SubTask 全部完成
→ Orchestrator 汇总初稿
→ 质量检查发现证据缺口
→ 创建 supplementary SubTask
→ 发布到同一任务队列
→ Worker 集群继续消费
→ 合并补充结果并修订报告

初始研究和补充研究复用同一套基础设施，只需要用阶段和轮次区分：

phase and iteration
{ "task_phase": "initial", "iteration": 1 }
{ "task_phase": "supplementary", "iteration": 2 }

最终回答不是“用消息队列就分布式了”，而是：持久化状态 + 可靠投递 + 可转移执行权 + 幂等事件 + 可恢复工作流，共同保证任何浏览器或单个进程消失后任务仍能继续。
基于当前 Deep Research 项目与分布式 Worker 讨论沉淀 · 重点：任务不依赖浏览器，不依赖单个 Worker，也不依赖单个 Orchestrator 进程。
