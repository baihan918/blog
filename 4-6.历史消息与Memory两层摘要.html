01 · CURRENT IMPLEMENTATION

它不是“两层摘要”，而是“一个可见面 + 一条完整日志”

每次请求由 session.deriveMessages() 投影当前 surface。压力不高时携带全部有效历史；压力达标后，旧段被一个结构化 checkpoint 替换。

🧠

模型当前看到的

一份最新累计 checkpoint，加上保留的近期原文。

  • 没压缩时是全部有效消息
  • 压缩后不堆叠多个摘要
  • 工具调用与结果不被拆开
📜

底层真正保存的

按 seq 追加的 SessionEvent 日志，包含原始消息、工具事件和历次压缩记录。

  • 压缩是 surface replace
  • 旧节点被 shadow，不是物理删除
  • 回放、恢复、审计都从日志派生
一句话：surface 是“本轮发给模型的有效剧本”，SessionEvent log 是“不改写的拍摄母带”。

03 · CUMULATIVE CHECKPOINT

第二次压缩：旧 checkpoint + 新旧消息 → 一个新 checkpoint

自动选段永远从 surface 头部开始。因此旧 checkpoint 会进入下一次摘要输入，与新退出近期区的消息合并。

04 · CONTEXT INJECTION

滚动摘要在对话中怎么用？

在当前项目里，它表现为 surface 上的最新累计 checkpoint。每次请求执行 deriveMessages() 时，这份 checkpoint 会与保留的近期原文一起投影给 LLM。

📦

“全量提供”指什么

指最新那一份 checkpoint 整体进入本轮消息，而不是只从它里截几句。

  • 只注入当前有效版本 S2
  • 不再同时注入已被替换的 S1
  • 作为结构化 user message 进入 surface
🗃️

它不等于全量历史

原始 SessionEvent 日志不会每轮整库发给模型，否则压缩就失去意义。

  • 早期原文被 checkpoint 代表
  • 近期消息保留现场细节
  • 原日志只在有查询通道时按需回查

举例：如果 1～80 条旧消息已被压缩，81～100 条仍在 surface，模型看到的是“最新 checkpoint + 81～100 原文”，而不是重新发送 1～100 条。
多主题边界：当前 compaction 会把仍有效的多主题信息合并进一份累计 checkpoint，没有自动按当前话题挑选摘要块。要做“用户换题后自动切换历史”，需要在 compaction 之外增加主题识别和可检索 Memory。
05 · SESSION EVENT LOG

日志是事实母带，Checkpoint 只是当前投影

SessionEvent[] 采用 append-only 追加方式，保留原始对话、工具过程和历次压缩记录。它不是每轮全量发给 LLM 的消息列表，而是用于重建、审计与回查的事实源。

🔎

三者的边界：SessionEvent 日志 = 完整事实档案；Checkpoint = 当前会话的压缩投影；长期 Memory = 筛选后、可跨会话复用的稳定知识。
一套权威数据，多种派生视图：后端不需要分别保存“聊天框历史”和“模型历史”。默认只持久化 SessionEvent 日志；聊天框可从原始事件渲染完整气泡，模型历史则由 surfaceOp 重放后通过 deriveMessages() 投影。可选搜索索引也是可删除重建的派生数据，不是第二套事实。
Shadow 不是 Delete：旧消息被 Checkpoint 从当前 Surface 遮蔽，但原始事件仍在日志中。这是能够重建、审计和找回细节的前提。
06 · WHEN TO COMPACT

压缩不看消息条数，主要看当前请求压力

totalTokens 估算的是当前请求整体压力，包含请求头开销和当前 surface，不是数据库中所有历史事件。

默认在 80% 触发

totalTokens ≥ contextWindow × 0.8 时，在下一个 step 前尝试压缩。

→
保留最近约 16%

从尾部按 token 累加保留原文，其余可压缩头部生成 checkpoint。

切分边界：当前实现按 token 预算从尾部保留，再回退到工具调用/结果平衡点；它没有主题分类器来寻找“语义分段”。
07 · COMPACTION FLOW

一次自动压缩到底发生了什么？

这是当前代码的真实顺序：先计量，再做无模型剪枝，最后才调用摘要模型并原子替换 surface。

1测量请求压力

TokenMeter.measure(session) 得到 totalTokens 和每个 surface node 的估算。

2先剪过大工具结果

可选 pruner 对超预算工具输出保留头尾；剪完重新计量，已安全就不调摘要模型。

3选择头部可压缩范围

尾部保留默认 16% 窗口 token，截点不得拆开 assistant tool call 与 tool result。

4生成结构化 Checkpoint

摘要器接收被选中的原文；如果包含旧 checkpoint，将仍有效信息与新消息合并。

5记录来源并替换

追加 compaction/summary，再追加一个 surfaceOp: replace 的 checkpoint user message。

收敛保护：新 checkpoint 必须比被替换内容更小。默认允许一次额外压缩尝试；仍无法降到阈值下则报错，不会假装成功。
08 · HISTORY RETRIEVAL

历史消息如果要检索，实际走哪条链路？

先看累计 checkpoint 是否保留了答案。若摘要遗漏，只有宿主挂载可选 tool-session-query 时，模型才能主动搜索原始事件。

CURRENT TURN

“很早之前定的端口号是多少？”

→
AVAILABLE EVIDENCE
1先查当前证据

模型先检查当前累计 Checkpoint 与近期原文；已有确切答案时不需要额外搜索。

2判断搜索范围

session_event_search 搜一个 session 的早期事件；session_search 搜同工作区其他 session，并排除调用方当前 session。

3检索候选摘录

当前 SQLite 提供方使用 FTS5 字面短语搜索；默认覆盖 current、shadowed 和 log-only 事件。

4精确读取原事件

命中摘录只用于定位。金额、端口、代码等精确问题继续使用 session_event_read 按 session id 与 seq 读取原始事件。

5带回后续 Step

读取结果作为工具结果写入本会话日志并进入当前 surface，模型依据原始证据作答；以后它也可能被 compaction。

谁决定要不要检索：模型根据当前问题和已有上下文主动调用工具；当前没有独立的主题分类器、向量路由器或固定相关度阈值替模型做决定。
默认限制：历史查询工具是 opt-in，已发布的默认宿主不挂载它。没有读取通道时，Agent 应说“当前上下文没有证据”，不应猜。
09 · MEMORY READ DECISION

Codex Memory 如何判断“这次要不要读”？

这里的“主模型”就是当前理解问题、规划步骤并调用工具的 LLM。它不是额外的记忆分类模型；当前读取路径是“摘要先导航、模型做相关性判断、工具按需检索”。

🧭

什么时倾向读取

问题提到历史项目、仓库、文件、用户偏好、过往决策或要求与之前保持一致；问题有歧义且可能依赖旧上下文时也应快速检索。

⏭️

什么时可以跳过

当前问题完全自包含，如简单翻译、一句话改写、格式转换或一条与项目无关的命令；额外记忆不会改变结果时不做推测性检索。

1摘要已经在场

memory_summary.md 在启用且非空时会预先进入 developer instructions；不需要先调用搜索工具才能看到导航摘要。

2语义判断在 LLM

没有固定的 if (intent === "memory") 分类服务。模型根据当前问题、摘要路由和开发者规则自主选择工具。

3工具调用是触发点

模型输出 function call；Runtime 执行搜索，再把结果作为 function-call output 回填给模型。默认可用 exec_command 执行 rg，开启 dedicated tools 时可直接用 memories.search/read。

4召回是字面检索

当前本地 Memory 读取是 Markdown 文件的关键词/子串匹配，支持同行或行窗口条件；未使用 embedding、余弦相似度或 reranker。

5模型二次筛选

文本检索只负责找到候选行；LLM 判断命中是否真的相关、是否需要继续读取 rollout summary，并对可能过期的信息回到当前代码验证。

memory-read-loop.ts · 机制伪代码
// memorySummary 已随 developer instructions 进入首次推理
const decision = mainModel.reason(userQuery, memorySummary, readRules)

if (decision.needsDetailedMemory) {
  // 这一步是模型发出工具调用，不是独立意图分类器强制执行
  const hits = await tools.memorySearch({
    queries: decision.keywords
  })
  const evidence = decision.needExactDetail
    ? await tools.memoryRead(hits.best.path)
    : hits
  return mainModel.answer(userQuery, evidence)
}

return mainModel.answer(userQuery)
一句话定位：这是“LLM 语义路由 + function tool + 文件关键词召回 + LLM 二次筛选”，不是“独立意图模型 + 向量数据库”。
不要与会话恢复混淆：当前 session 的历史消息由会话日志/surface 自动恢复，不经过这个“是否搜 Memory”判断；本节说的是跨任务长期记忆。
10 · RETRIEVAL TYPES

FTS5 是关键词检索的一种实现，不等于向量检索

“关键词检索”是能力类别，SQLite FTS5 是具体全文引擎。它先分词并建立倒排索引，再按词或短语命中；向量检索则比较 embedding 的语义距离。

方式匹配依据擅长主要缺口
LIKE / 包含扫描字符串是否包含查询文本少量数据、临时查找大语料扫描成本高，缺少相关度能力
SQLite FTS5分词后的字面 token / 短语文件名、函数名、端口、错误码和原话用户换一种说法时容易漏召回
向量检索问题与文档 embedding 的距离同义改写、模糊回忆和概念相近内容精确值可能被相似内容干扰，可解释性较弱
混合检索关键词候选 + 向量候选同时覆盖精确值与语义表达需要融合排名、评测和索引版本治理
🔤

字面命中

原文是“API 服务监听 8787 端口”，搜索“端口”时 FTS5 很合适。当前实现把输入当作规范化字面短语，OR、NEAR、* 不作为查询语法执行。

🧭

语义命中

用户改问“当时网络配置怎么定的”，原话没有“网络配置”时，关键词可能落空；向量可以把它与“服务监听端口”关联起来。

选择结论：查原话和精确值，FTS5 更稳；查相同意思，向量更强；面向长期真实使用，通常让两路各取 TopK，再用 RRF 或 rerank 合并。
11 · POSTGRESQL DESIGN

迁移 PostgreSQL：强日志不变，搜索作为派生投影接在后面

推荐让 PostgreSQL 同时承载权威 SessionEvent 日志与可重建搜索投影，但使用不同 schema 隔离职责。安装 pgvector 后，PostgreSQL 可以同时完成关系过滤、关键词检索与向量近邻搜索。

事务主链
dsh_log
append SessionEvent+校验连续 seq+写 indexing outbox
异步投影
dsh_search
提取事件文本→长内容切块→生成 embedding→写关键词与向量索引
在线查询
Hybrid
关键词 TopK+向量 TopK→RRF 合并→按 seq 回读强日志
📜

PostgreSQL 持久化插件

新增 session-persistence-postgres，实现现有 SessionPersistence 的 create、append、load、inspect、readFrom、list 与 listSnapshots。

🧱

日志事务约束

以 (session_id, seq) 为主键；append 时锁定 session 行，校验起始 seq 和批次连续性，然后更新 next_seq 与 revision。

🔎

混合查询插件

新增 PostgreSQL Session Query 提供方；授权过滤必须在关键词和向量两条候选查询中同时生效，最终仍按 seq 读取原事件。

postgresql-schema.sql · 结构示意
CREATE TABLE dsh_log.session_events (
  session_id text, seq bigint, type text, time timestamptz,
  data jsonb, source_event_seqs bigint[], surface_op jsonb,
  PRIMARY KEY (session_id, seq)
);

CREATE TABLE dsh_search.documents (
  session_id text, seq bigint, chunk_no integer,
  cwd text, surface text, content text,
  text_search tsvector, embedding vector(1536),
  content_hash text, embedding_model text,
  PRIMARY KEY (session_id, seq, chunk_no)
);

CREATE INDEX docs_fts
  ON dsh_search.documents USING gin(text_search);
CREATE INDEX docs_vector
  ON dsh_search.documents USING hnsw
  (embedding vector_cosine_ops);
为什么要 Outbox：事件日志与待索引任务在同一事务提交；embedding 在事务外异步生成。模型服务超时不会阻塞会话落盘，失败任务可以重试，关键词索引也可以先于向量结果可用。
中文关键词检索：PostgreSQL 内置 tsvector 不应被当作完整中文分词方案。可在应用层预分词，并用 pg_trgm 补充中文片段、路径和错误码；向量负责语义改写召回。
12 · PGVECTOR OR MILVUS

当前阶段不必引入 Milvus，先让 pgvector 承担向量投影

PostgreSQL 不是原生向量数据库，但安装 pgvector 后支持向量类型、距离计算、精确近邻和 HNSW / IVFFlat 近似索引。Milvus 则是以分布式向量检索为中心的独立系统。

维度PostgreSQL + pgvectorMilvus
系统定位关系数据库增加向量能力专用分布式向量数据库
强日志事务、唯一约束、连续 seq 和 JSONB 很适合不建议取代 SessionEvent 的关系型事实存储
混合检索FTS / pg_trgm + pgvector，再用 SQL、RRF 或 cross-encoder 融合原生支持 dense、sparse/BM25、多向量搜索与融合
过滤与关联cwd、session、时间、事件类型和 JOIN 表达能力强适合检索标量过滤，不面向复杂关系事务
扩展方式先垂直扩展，再结合副本、分区或分布式 PostgreSQL 方案面向大规模向量集合的独立水平扩展
运维成本已有 PostgreSQL 时较低，无跨库同步增加集群、同步、索引一致性和监控成本
✅

优先 pgvector

会话历史以强日志为中心、向量规模尚未证明 PostgreSQL 是瓶颈时，将日志、授权字段和两类索引放在同一数据库最简单可靠。

↗️

何时再上 Milvus

只有压测证明 pgvector 的吞吐、延迟、索引内存或多模态能力不能满足目标，并且需要独立扩容检索资源时再引入。

14 · CODE PATH

用接近项目实现的伪代码串起全流程

关键不是维护一个可变的 rolling_summary 字段，而是对 append-only 事件日志投影 surface，用 replace 节点表示当前 checkpoint。

compaction-flow.ts · 项目机制伪代码
async function beforeStep(agent) {
  let measurement = tokenMeter.measure(agent.session)
  const contextWindow = await resolveContextWindow(agent)
  const threshold = Math.floor(contextWindow * 0.8)

  if (measurement.totalTokens < threshold) return

  // 先做无模型剪枝：过大工具结果保留头尾
  toolResultPruner?.pruneSession(agent.session)
  measurement = tokenMeter.measure(agent.session)
  if (measurement.totalTokens < threshold) return

  // 尾部默认保留 16% token，而且不拆 tool call/result
  const retainTokens = Math.floor(contextWindow * 0.16)
  const range = selectCompactableRange(
    agent.session, measurement, retainTokens
  )
  if (!range) return

  // range 从 surface 头部开始，可能包含上次 checkpoint
  const summary = await summarize(
    buildSummarizationInput(agent.session, range)
  )
  assertSmaller(summary, range)

  session.append("compaction/summary", { summary, sourceSeqs: range })
  session.append("user/message", frameSummary(summary), {
    surfaceOp: { op: "replace", ...range }
  })
}

// 每次真正请求只投影当前 surface
request.messages = agent.session.deriveMessages()
15 · CAPABILITIES & GAPS

当前方案解决了什么，又没有解决什么？

✅

可重建

模型可见内容都能从日志重建，压缩替换还记录被遮蔽的来源 seq。

🧱

结构安全

压缩切点保护工具调用/结果成对关系，且拒绝不能缩小原文的摘要。

⚠️

摘要会衰减

累计 checkpoint 多次重写可能丢失早期细节；原日志保住了事实，但不保证模型自动找回。

🔎

检索不是默认兜底

历史工具必须显式挂载，且由模型决定是否搜、用什么字面查询。
