01 · Mental Model

多跳的关键：下一问由上一问决定

复杂问题通常无法用一次检索直接命中答案。系统需要取得中间事实，再把中间事实带入下一次查询。这里的“跳”指证据依赖，不是循环次数。

原始问题OpenAI CEO 出生城市所在州的州长是谁？
Hop 1查 CEO 是谁
Hop 2查他的出生城市
Hop 3查城市属于哪个州
Hop 4查该州当前州长并回溯证据
模式查询之间的关系典型结构是不是多跳
重复搜索每次都搜索同一句话Q → Q → Q不是
查询改写根据结果换一个更好的搜索词Q₁ → Q₂ → Q₃轻量级
事实多跳下一问必须使用上一跳抽取的事实事实 A → 查询 B → 事实 C是
DAG 多跳多个依赖分支并行，之后汇合验证A → {B,C,D} → E完整版
02 · Repository Reality

当前项目：有迭代搜索，还没有原子子问题 DAG

Researcher 已经形成“搜索—判断充足度—生成新查询—再次搜索”的闭环，所以可以称为简化版多跳搜索；Memory 的向量加关键词融合则是 Hybrid Retrieval，不是多跳。

✓

已经实现

  • max_iterations 控制最大搜索轮数
  • LLM 根据本轮结果判断 is_sufficient
  • 信息不足时生成 new_query
  • 所有轮次结果去重后生成带来源报告
△

还没有实现

  • 把复杂问题拆成可验证的原子子问题
  • 显式保存每一跳的事实与证据
  • 对子问题建立依赖图并分别追踪完成度
  • 运行时根据上游结果动态增加分支
core/agents/researcher.py · 当前主链路ITERATIVE SEARCH
for i in range(max_iterations):
    results = await web_search.search(current_query)

    is_sufficient, new_query = await evaluate_and_refine(
        original_query=query,
        current_query=current_query,
        results=results,
    )

    if is_sufficient:
        break
    current_query = new_query
准确定位：项目目前是“单链迭代查询 + 固定/临时 Agent 工作流”，还不是“原子子问题 + 事实状态 + 动态 DAG”的复杂多跳系统。
03 · Planning vs Retrieval

LLM 负责理解和规划，DAG 负责调度，检索器负责真正查资料

可以把复杂多跳理解成“语义规划 + 任务调度 + 信息获取”，但不能说“DAG 做检索”。DAG 只表达哪些任务先做、哪些可以并行、哪些必须等待汇合；Web Search、向量数据库或业务数据库才是真正执行检索的组件。

用户问题自然语言复杂目标
LLM Planner识别语义、实体、子问题与依赖
DAG / Scheduler按依赖调度串行、并行与汇合节点
Web Search联网搜索
Vector Store语义召回
Database结构化查询
Synthesizer + Critic汇总证据、检查遗漏与冲突
组件核心职责不负责什么
LLM Planner理解问题、拆子问题、生成依赖、必要时规划下一跳不直接替代搜索引擎或数据库
DAG表达子问题之间的串行、并行和汇合关系不读取网页，也不计算向量相似度
Scheduler寻找 ready 节点、控制并发、重试、超时和状态不决定搜索结果是否真实
Retriever / Search执行关键词、向量、Web 或数据库检索通常不负责完整任务规划
Researcher LLM生成搜索词、抽取事实、判断信息是否充足不应该绕过来源直接编造事实
Synthesizer / Critic合并分支结果、验证证据覆盖和冲突不应把缺失证据包装成确定结论
A

先拆解，再用 DAG 调度

适合子问题能提前明确，并且存在并行和汇合关系的任务。

  • LLM 一次生成子问题和 dependencies
  • Scheduler 执行完整任务图
  • 适合公司对比、产业研究、跨来源核验
B

边检索，边生成下一跳

适合下一问必须看到本轮事实后才能确定的链式问题。

  • 搜索当前 query
  • LLM 抽取事实并判断缺失信息
  • 生成 new_query，循环直到充足
当前项目的真实嵌套关系OUTER DAG + INNER LOOP
CEO 的 SOP DAG
│
├── Researcher 节点
│      └── for iteration in max_iterations:
│             results = await search(current_query)
│             sufficient, new_query = await evaluate(results)
│             if sufficient: break
│
├── Analyst 节点
└── Critic 节点
当前项目的结论：DAG 调度的是 Researcher、Analyst、Critic 等 SOP 节点；Researcher 内部每一跳搜索由 for 循环控制，并没有把 Query 1、Query 2、Query 3 分别建成 DAG 节点。
真实项目常用组合：外层 SOP DAG 管理稳定阶段，中层 Map 展开未知数量对象，内层 Researcher 循环生成下一跳；只有异常结果改变任务结构时，才触发局部重规划。

05 · Fan-out / Fan-in

中途并行：一个 SOP 先串行，再分叉，再汇合

并行不是从入口就拆成两个 SOP。只要多个节点依赖同一个已完成节点，它们就会同时进入 ready 集合；下游节点依赖所有分支时，就会等待它们全部完成。

scope确定研究范围
market_size依赖 scope
competitors依赖 scope
policy依赖 scope
synthesis等待三个分支全部完成
final_review审核综合结论与证据
scope没有前置依赖BATCH 1
market / competitor / policy都只依赖 scope，因此同批就绪BATCH 2 · PARALLEL
synthesis依赖三个研究分支，必须等待全部完成BATCH 3 · JOIN
final_review依赖 synthesisBATCH 4
不要人为写 parallel: true：并行性最好从依赖图推导。否则“声明并行”与真实依赖冲突时，调度器很难判断该相信谁。
06 · Interactive Scheduler

点一次“执行下一批”，看 ready 集合怎样变化

调度器不是预先决定第几步，而是每轮扫描 pending 节点：只要所有依赖都在 executed 集合中，该节点就进入 ready；同一轮的 ready 节点使用 asyncio.gather() 并行执行。

DAG 执行模拟器

紫色 = 本批可并行执行，绿色 = 已完成，灰色 = 依赖未满足。

准备执行 · Batch 1
scopedeps: []
market_sizedeps: [scope]
competitorsdeps: [scope]
policydeps: [scope]
synthesisdeps: [market, competitors, policy]
final_reviewdeps: [synthesis]
Readyscope 没有依赖，所以首先进入 ready。
core/agents/ceo.py · 项目已有的批次调度TOPOLOGICAL EXECUTION
while pending:
    ready = [
        node_id for node_id, node in pending.items()
        if all(dep in executed for dep in node.dependencies)
    ]

    results = await asyncio.gather(
        *[execute_and_track(node_id) for node_id in ready]
    )
07 · Runtime Expansion

如果分支数量事先不知道，就需要 Map 或动态扩图

“研究市场、竞品、政策”在规划时已经知道三个分支，普通 DAG 足够；“先找出所有目标公司，再逐家公司调研”要等上游返回列表后才知道分支数量，静态 SOP 无法提前写完整。

①

动态扩展 DAG

discover_companies 完成后，调度器插入 research_company_1...N，再补一个依赖全部分支的汇合节点。

  • 可观察性最清楚
  • 图校验和恢复更复杂
  • 适合长任务平台
②

Map 节点

SOP 只保留一个逻辑节点，执行器对上游列表中的每个 item 并发调用同一 Agent，最后收集数组结果。

  • SOP 更紧凑
  • 容易限制并发与失败比例
  • 适合批量同构任务
建议扩展的 Map 节点协议NOT YET IMPLEMENTED

08 · Production Choice

“稳定骨架 + 受控展开 + 局部重规划”不等于只有 Map

Map 只是中间那段“受控展开”的常用实现。真实项目通常把三种能力组合起来：骨架决定必须经过哪些质量阶段，Map 处理数量未知但结构相同的批量任务，局部重规划处理少数无法套用统一模板的异常对象。

稳定骨架发现 → 校验 → 研究 → 汇总 → 审核
discover + validate去重、过滤、排序、限制 Top-N
Map: company A统一研究模板
Map: company B统一研究模板
Map: company C发现特殊情况
局部重规划 C只替换异常分支，不推翻整张 SOP
synthesis + review汇总结构化结果，检查证据与缺失项
能力解决的问题什么时候使用是否等于 Map
稳定骨架整体必须经过哪些阶段和质量门流程稳定、需要审计和恢复不是
Map对未知数量对象执行相同任务逐家公司、逐篇论文、逐个文件处理就是 Map 本身
条件分支有限类型采用不同固定流程上市公司查财报，创业公司查融资不是
局部重规划执行结果改变某个分支的后续结构发现收购、实体冲突或证据不足不是
全程动态规划每一步之后才决定下一步高度开放、路径完全未知的探索不是，且不应默认使用
🧭

默认选型

大多数业务任务先使用“固定骨架 + Map + 重试/失败策略”。等真实需求证明统一模板处理不了少数对象，再加入局部重规划。

  • 已知固定分支：普通 DAG dependencies
  • 未知数量、同构处理：Map
  • 有限类型差异：条件路由
  • 结构被结果改变：局部重规划
🚧

为什么不默认一步一规划

全动态规划虽然灵活，但 LLM 调用、延迟和不可预测性都会增加，容易重复搜索、无限规划，也更难做测试、成本控制和断点恢复。

  • 只允许特定节点或 Critic 触发重规划
  • 只替换尚未执行的局部子图
  • 已完成且证据有效的节点继续复用

⏱

资源边界

max_items、max_concurrency、单项超时和总预算必须由执行器强制执行，不能只写进 Prompt。

↻

失败边界

按任务选择 fail_fast、allow_partial 或最低成功率，并把失败对象明确写进报告。

▦

数据边界

Map 子任务返回统一 JSON：业务、融资、证据、置信度和缺失字段，避免汇合节点解析自由文本。

当前项目的并行风险：_execute_sop() 会把同一个 context 字典传给并行节点，而审核流程又会写入 review_feedback、content 等字段。扩展 Map 前应为每个节点复制隔离的 node_context，并行任务只通过返回值汇合，不能直接修改共享上下文。
一句话判断：全部对象走相同流程，用 Map；对象只有几种已知类型，用条件分支；某个对象在执行中暴露了新的未知流程，才对该分支局部重规划。
09 · Project Boundary

项目基础设施已经能跑静态 DAG，缺的是规划协议与动态节点

不要把所有能力都塞进 Researcher 的搜索循环。Planner 负责拆题与依赖，Scheduler 负责调度，Researcher 负责单个研究节点，Synthesizer 负责汇合，Critic 负责证据与完成度检查。

CEO._generate_sop()

已经能让 LLM 临时生成 SOP，但 Prompt 尚未强制“原子子问题、证据产物、完成条件”。

CEO._execute_sop()

已经通过 dependencies 找 ready 节点，并用 asyncio.gather 执行同一批节点，支持规划时已知的中途并行。

CEO._render_template()

已经支持 {{results.node_id}} 引用上游结果，但目前主要抽取 summary 或截断后的字符串。

Researcher._iterative_research()

已经支持单个研究节点内部的迭代查询改写，可以作为 DAG 中每个 Researcher 节点的执行器。

待新增 MapNode

用于根据上游列表运行时展开并行任务，并配置最大并发、失败策略、重试和结果汇合。

能力层级结构当前状态下一步
查询改写Q₁ → Q₂ → Q₃已实现记录每轮缺失信息与事实
静态 DAGA → {B,C} → D调度器已支持强化 Planner 拆题协议

动态分支A → Map(items) → D未实现增加 MapNode 或动态图扩展
证据级多跳事实状态 + 引用 + 完成条件未完整实现引入结构化 Fact/Evidence 输出
推荐架构：固定 SOP 骨架约束质量门，Planner 在骨架内部生成临时子问题 DAG；已知分支用 dependencies，自发现列表用 Map；所有汇合节点只消费结构化结果和可追溯证据。
10 · Checkpoint

用六个问题检验是否真正理解

答完后，你应该能在面试中清楚解释：为什么复杂多跳不是简单循环，以及 DAG 怎样自然表达中途并行。

1. 同一句 query 搜索三次，算多跳吗？

多跳的本质是信息依赖，不是调用次数。

2. 一个 SOP 中三个节点都只依赖 scope，会怎样？

项目调度器根据 dependencies 推导 ready，而不是只看数组顺序。

3. 什么时候必须引入 Map 节点？

规划时已知的并行分支，普通 dependencies 已经足够。

4. 当前项目的 Memory Hybrid Search 是多跳吗？

Hybrid Retrieval 描述检索通道组合；Multi-hop 描述前后事实依赖。

5. “稳定骨架 + 受控展开 + 局部重规划”等于 Map 吗？

骨架负责阶段和质量门，Map 负责同构批量任务，局部重规划负责特殊分支的结构变化。

6. 多跳系统中的 DAG 会直接执行检索吗？

LLM 负责理解和规划，DAG 表达依赖，Scheduler 调度，Retriever 或 Search 才执行真正的信息查询。
面试一句话：“我会把复杂查询规划成一个临时 DAG：有依赖的节点串行，无依赖且同时 ready 的节点并行，汇合节点等待所有上游；如果分支数量运行时才确定，则用 Map 节点或动态扩图。”
