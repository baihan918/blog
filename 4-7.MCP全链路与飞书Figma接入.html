01 · MENTAL MODEL

把 MCP 想成“工具插座标准”

Agent 不需要提前认识每一个平台。只要某个 Server 遵循 MCP，它就能用统一方式询问“你会什么”、调用能力并读取结果。

🧠

Agent / LLM

理解用户意图，从当前工具清单里决定是否调用、调用哪个、参数是什么。

⌁

MCP Host / Manager

通过 Streamable HTTP 连接多个 Server，动态收集 schema，并按命名空间路由调用。

⚙

Connector + Writer

Connector 读取外部数据；Writer 在应用侧生成 Markdown、HTML、JSON 与图片，两者不互相越权。

一句话：模型只生成“调用哪个工具、传什么参数”的意图；Codex / Agent Runtime 这样的宿主才连接 MCP、执行本地 handler、管理权限并把结果放回模型上下文。
02 · LIFECYCLE

一次 MCP 调用，实际走了 8 步

点击任一步，查看这一刻是谁在做什么。前四步建立能力清单，后四步完成一次工具调用闭环。

1. 注册 Server

应用登记两个 Streamable HTTP 地址：Feishu Connector 与 Figma Connector。它们可由桌面端启动，也可单独部署后供多个 Agent 使用。

关键：工具不是写死在模型 prompt 里。每次测试都会先连接 Server 并执行 tools/list，再把当下真实存在的工具交给模型。
03 · ORCHESTRATION

同一个 MCP，可以有两种使用方式

是否“自主选择”由调用它的上层流程决定，不是 MCP 自己决定。

Workspace：固定编排

用户点击明确入口，应用直接调用飞书 Connector；拿到只读数据后，再交给 Writer 生成文档，无需模型判断。

button → feishu/read_document → writer

VS

全栈 Tab：Agent 自主选择

把 MCP 动态发现的工具交给模型。模型选择数据源，Connector 返回数据，应用再确定性地调用对应 Writer。

prompt → LLM → connector → writer

隔离原则：当前自主调用入口是独立旁路测试，不进入、也不修改已有 FullStackAgent / OODA / Codex 任务链路。
04 · FEISHU MCP

飞书：HTTP Connector 只负责“读”

对 Agent 暴露 read_document：完成 wiki 定位、正文、blocks 与图片临时地址读取，但不接收 Workspace 路径，也不生成文件。

飞书读取链路

拆分后的关键：

Connector 冻结“读 wiki → 找 docx → 拉正文 → 拉 blocks → 取媒体临时地址”；Writer 冻结“下载图片 → 渲染 Markdown / HTML → 安全写入 Workspace”。读取能力可以被其他 Agent 复用，而写入策略仍由各应用自己控制。

🔑

服务端认证

FEISHU_APP_ID 与 FEISHU_APP_SECRET 只进入 Feishu Connector 环境；tenant access token 由 lark-mcp 按需获取。

🖼

图片

先从文档 blocks 找图片 token，再取得临时下载地址，将真实图片写入同一文档包的 assets/。

05 · FIGMA MCP

Figma：HTTP Connector 包装 REST API + PAT

Figma Connector 使用 PAT 调 REST API，只返回节点结构与临时预览地址；真实 PNG 和 JSON 由 Workspace Writer 落盘。

Figma 读取链路

Agent / 页面提供包含 node-id 的设计链接
MCP Manager动态发现 figma 工具并路由

PAT 认证X-Figma-Token，仅后端持有

Workspace Writerdesign.json + preview.png
本质是什么？

对上仍然是标准 Streamable HTTP MCP；对下是 Figma REST API。PAT 不会发给 Agent、模型或 Workspace Writer，Writer 只消费 Connector 返回的结构数据和短期预览地址。

⌗

结构数据

节点树保留文本、布局、尺寸、颜色、圆角、组件引用等核心设计信息，并限制最大节点数，避免上下文失控。

▣

视觉数据

对目标 node-id 请求 PNG 渲染，真实图片落到 assets/preview.png，与结构 JSON 共同提供设计上下文。

07 · DEPLOYMENT & CONFIG

Server 单独部署，配置和凭证跟着服务走

桌面开发模式会在随机本地端口启动两个 HTTP 进程；团队模式则把它们部署到容器、函数计算或 Kubernetes，通过 URL 注册给多个 Agent。

☁

Feishu Connector

持有 FEISHU_APP_ID、FEISHU_APP_SECRET；内部获取 tenant token。其他 Agent 只知道 MCP URL。

◆

Figma Connector

持有 FIGMA_PAT；通过 X-Figma-Token 访问 REST API，不把 PAT 放进工具返回。

⌂

Workspace Agent

只持有两个 Connector URL 与自己的访问凭证；写入目录和文件策略留在本应用。

当前配置

本地从进程环境或 .env 读取 URL、第三方凭证和 Connector Bearer Token；工具注册仍由应用 registry 管理。

Apollo 演进

可按 Feishu、Figma、Workspace 三个应用/Namespace 分发配置；Apollo Access Key 本身必须由部署平台 Secret 注入，不能依赖 Apollo 自举。

Bearer Token 的角色：它认证“哪个 Agent 正在调用 Connector”，不等于飞书 tenant token，也不等于 Figma PAT。生产环境应逐 Agent 发放独立短期凭证，并配工具权限、审计与撤销。
08 · NATIVE MCP VS ADAPTER

对模型都是调用意图，区别在宿主执行路径

LLM 不会亲自执行 HTTP、MCP 或本地代码。它只输出工具名和参数；宿主收到意图后，选择本地 handler，或通过 MCP Client 转发给 MCP Server。

Function Tool

LLM → tool_call → Host 中预注册的 handler。handler 可以执行本地代码，也可以继续请求远程 HTTP 服务；Function Tool 并不等于“只能本地”。

MCP Tool

LLM → tool_call → Host 的 MCP Client → tools/call → MCP Server。Server 既可以是本机 stdio 子进程，也可以是远程 HTTP 服务；MCP 并不等于“只能远程”。

维度Function ToolMCP Tool
模型看到什么工具名、描述、参数 schema工具名、描述、参数 schema
谁真正执行宿主绑定的 handler宿主中的 MCP Client 转发给 Server
工具如何注册应用预先编写和注册通过 tools/list 动态发现
部署位置本地或远程本地 stdio 或远程 HTTP
跨宿主复用通常需要重新集成通过标准协议更容易复用
准确结论：MCP 可以理解为把工具发现、schema、调用、结果、资源和连接管理标准化。当前本地测试由 Manager 把 MCP 工具适配成模型 Function Tools；支持托管 MCP 的模型服务，则由服务端工具运行层承担 Host 的一部分职责，而不是 LLM 本体直接连接 MCP。
09 · HOST & FILE DATA PLANE

大文件不进上下文，走宿主的数据通道

普通 MCP 文本结果最终会变成模型的 tool result，内容过大时会被限长。文件字节应在远程服务与实际执行环境之间传输，LLM 只接收 fileId、路径、摘要与校验结果。

远程文件落到桌面并生成产物

CONTROL PLANE ≠ DATA PLANE
LLM返回 export_document 的工具调用意图
Codex Host通过 MCP Client 执行 tools/call
远程 MCP生成 fileId、元数据与短期下载凭证
文件数据通道宿主流式下载，不把字节放进 prompt
本地 Writer完整读取、转换、生成与验证
LLM / 用户只看到结果摘要与本地最终路径
为什么远端路径没用？

/tmp/source.docx 只属于远程 MCP Server 的文件系统。Codex 桌面端不能凭这个字符串读取文件；必须拿到可下载的文件句柄，或把文件复制进当前执行环境，再由本地 Writer 处理。

⌁

控制面：给 LLM 的小结果

工具名、参数、fileId、文件名、大小、MIME、哈希、过期时间、最终路径和验证摘要。它们用于决策，可以安全进入模型上下文。

⇣

数据面：不给 LLM 的大字节

文档、图片、压缩包和生成物通过流式下载、共享对象存储或执行环境文件 API 传输，直接落到受控临时目录。

1

机械转换

远程或本地程序直接处理完整文件，只把结果交给模型。例如 PDF 转 DOCX、Excel 转 CSV、模板填充。

2

语义生成

文件先落地，再由本地解析器按页或章节分块；LLM 逐块提取结构化事实，Writer 最后组装并回查原文。

3

远端生成

MCP Server 在远端直接生成最终产物并返回新的 fileId；桌面端只下载成品，再做本地校验和展示。

不能这样做：只返回远端 /tmp 路径，本地不可访问；把几十 MB 文件转成 base64 放进 MCP 文本结果，会消耗上下文并可能被截断。若没有下载、执行环境复制或分块读取能力，就不能保证完整生成。
10 · SAFETY BOUNDARIES

稳定接入靠边界，不靠模型“自觉”

认证、文件范围、网络目标和输出体积都应由应用与 Server 强约束。

凭证边界

Secret 与 PAT 只在对应 Connector 环境中；Agent 只持有 MCP 访问凭证。任何凭证都不能写进 prompt、工具结果、日志或前端状态。

链接边界

飞书只接受可信飞书域名；Figma 只解析 figma.com HTTPS 链接。链接只是定位资源，不允许变成任意网络请求入口。

写入边界

Connector 永不写 Workspace；Writer 才能把生成物落到指定测试目录，并防止符号链接把写入位置引出 Workspace。

内容边界

MCP 返回内容属于不可信数据，只能当资料使用，不能把文档或设计里的文字提升成系统指令。

体积边界

限制节点数量、字符串长度与图片大小；图片优先传临时 URL，由 Writer 下载，避免在 MCP 响应中塞入大段 base64。

传输边界

下载凭证必须短期、单文件、最小权限并校验大小、MIME 与哈希；临时文件名不能直接信任远端输入，最终产物只能写入获准目录。

11 · QUICK CHECK

四题确认你真的理解了

每题选择后会立即显示答案。

1. Connector 可以直接写 Workspace 吗？

Connector 是可复用的数据连接器，Workspace 写入属于具体应用的副作用边界。

2. PAT 能否直接登录官方 Remote MCP？

PAT 是 REST API 凭证，不等于官方 Remote MCP OAuth。

3. MCP 必须转换为 Function Tool 吗？

Chat Completions 需要 Host 适配；支持原生 MCP 的 Responses API 可直接使用 type: mcp。

4. 远端 MCP 返回 /tmp/a.docx，本地能直接读取吗？

路径只在它所属的文件系统中有效；大文件应走宿主数据通道，而不是进入 LLM 上下文。
