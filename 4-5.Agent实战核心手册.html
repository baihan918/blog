01 · DECISION BOUNDARY

先判断：这个问题真的需要 Agent 吗？

Agent 不是默认答案。不确定性越高、步骤越难预先写死，才越值得把部分决策权交给模型。

01 函数 / 脚本

输入输出确定，步骤可完整枚举。例：格式转换、固定校验。

不要 Agent
02 Workflow

步骤确定，但部分节点需要 LLM。例：摘要 → 分类 → 生成。

代码定路
03 Tool Loop

模型需要在少量工具中动态选择，但任务边界清晰。

单 Agent
04 Agent System

需要根据中间结果重新规划、回退、追问或终止。

状态机
05 Multi-Agent

存在真实的专业分工、并行需求或对抗审核，且收益超过协调成本。

最后选择
常见误区：把一串固定 LLM 调用命名为 Agent。判断关键不是“有几个 Prompt”，而是系统是否会基于环境反馈动态决定下一步。
02 · THE LOOP

Agent 的最小执行闭环

点击每一步，观察“模型负责什么”与“运行时负责什么”的边界。

Observe · 先看清现场

输入不只是用户的一句话，还包括当前状态、历史记录、可用工具、权限、预算和最新环境反馈。运行时应在这里做上下文裁剪与敏感信息过滤。

一句话心法：模型是不稳定的决策器，工具是可发生副作用的执行器，状态机是稳定的秩序维护者。
03 · ANATOMY

一个能上线的 Agent，至少有七个部分

框架名字会变，但这些职责始终存在。学会按职责读代码，比记 API 更稳固。

Model

理解、推理、生成候选行动；它不应直接拥有无限权限。

LLM / VLM
Context

系统指令、任务、环境、检索证据与历史的当前切片。

prompt + evidence
Tools

把意图变成读取或写入行为；必须有 schema、错误语义与幂等设计。

name / args / result
State

保存当前阶段、中间产物、错误、迭代次数和已执行副作用。

working memory
Orchestrator

控制路由、并发、超时、重试、回退、暂停、恢复和终止。

loop / graph / queue
Guardrails

工具白名单、参数校验、权限检查、人工审批、成本和步数上限。

policy + budget
Observability

记录每次决策、工具调用、状态变化、耗时、成本与质量指标。

trace / log / eval

05 · SEARCH VS EXTRACTION

Bocha 和 Trafilatura：一个找网页，一个读网页

这两个组件不是重复实现，而是信息获取流水线的上下游。理解它们的输入输出，比只记住库名更重要。

组件它解决的问题输入输出不负责什么
Bocha Web Search全网哪些页面与查询有关？搜索词，如“2025 新能源汽车销量”排序后的 URL、标题、摘要、来源和日期不保证读取了每个页面的完整正文
Trafilatura已知网页的 HTML 中，哪些是正文？某个已下载页面的 HTML过滤导航、广告和页脚后的纯文本正文不搜索全网，也不按研究问题发现和排序 URL
研究问题query
Bocha发现候选网页与 URL
requests / Browser下载选中页面的 HTML
Trafilatura去噪并提取正文
LLM + Verifier提取事实、核对证据
什么时候可以不用 Bocha？用户已经给出明确 URL，或者系统已经有一组确定的种子页面时，可以直接下载 HTML 并交给 Trafilatura。如果输入只是开放问题，Trafilatura 不知道应该读哪些网页。
当前 scout.py 的真实路径：主流程调用 _execute_search() 取得 Bocha 的 summary/snippet，然后由 _analyze_search_results() 直接分析摘要。Trafilatura 只在 deep_read_url() 里被使用，而该方法目前没有接入主调用链。所以现阶段更准确的描述是“搜索摘要分析”，不是已完成的“逐页深读原文”。

Python 导入语法：导入模块，还是只取其中一个名字？

trafilatura 是 Python 第三方库。下面两种导入方式都合法，差别在于当前文件里保留了哪个名字。

📦

导入整个模块

import trafilatura 会在当前作用域保留模块名。调用时写 trafilatura.extract(html)，能直接看出 extract 来自哪个库，也更不容易与同名函数冲突。

🎯

从模块取出指定对象

from datetime import datetime 从 datetime 模块中取出同名的 datetime 类。之后可直接写 datetime.now()，而不是 datetime.datetime.now()。

import_styles.py · 四种等价对照
# 1. 导入整个第三方模块
import trafilatura
text = trafilatura.extract(html)

# 2. 只导入模块中的 extract 函数
from trafilatura import extract
text = extract(html)

# 3. 导入 datetime 模块
import datetime
now = datetime.datetime.now()

# 4. 从 datetime 模块导入 datetime 类
from datetime import datetime
now = datetime.now()
选择原则：希望调用处明确显示来源，或模块里会用到多个成员时，倾向 import module；只频繁使用一两个名字且不容易冲突时，可以用 from module import name。
06 · ENGINEERING

Agent 从 Demo 到生产，主要难在哪里？

生产问题通常不是“模型不够聪明”，而是契约、状态、副作用和质量门没有被系统化。

核心点Demo 式思路生产式思路关键问题
工具契约能调到就行结构化参数、超时、错误分类、幂等键、权限重试会不会重复写入？
状态设计把对话全塞给模型显式阶段、产物、错误、版本和 checkpoint中断后从哪里恢复？
控制流让模型决定一切确定性骨架 + 受限的动态路由什么时候必须停？
可靠性失败就重试按错误类型重试、降级、补偿或求助错误是暂时还是永久？
可观测性只看最终答案步骤 trace、工具入参/出参、状态 diff、耗时和成本答错是错在哪一步？
评估“感觉答得不错”任务成功率、轨迹正确性、引用完整性、成本和延迟换模型后真的更好吗？
07 · MINIMAL SKELETON

不依赖框架的 Agent 最小骨架

这段伪代码刻意不写某个 SDK，只保留实战中必须存在的控制点。

agent_runtime.py · framework agnostic
async def run_agent(task, runtime):
    state = await runtime.load_or_create_state(task)

    while state.step_count < state.max_steps:
        observation = await runtime.observe(state)
        decision = await runtime.model.decide(
            context=runtime.build_context(state, observation),
            tools=runtime.allowed_tools(state)
        )

        if decision.type == "finish":
            verdict = await runtime.verify(decision.result, state)
            if verdict.passed:
                return await runtime.commit(decision.result, state)
            state = runtime.record_failed_verification(state, verdict)
            continue

        call = runtime.validate_and_authorize(decision.tool_call, state)
        result = await runtime.execute_idempotently(call)
        state = runtime.reduce(state, call, result)
        await runtime.checkpoint(state)

    return await runtime.escalate(
        reason="step_budget_exhausted", state=state
    )
🧠

模型做候选决策

decide() 可以不确定；它的输出只是一个待校验的行动提案。

🛡️

运行时做确定控制

授权、执行、幂等、验证、持久化和预算终止都不交给模型。

08 · FAILURE PLAYBOOK

常见失败模式：不要只靠“再试一次”

先分类，再处理。没有诊断的重试，往往只是更贵地重复失败。

LOOPING
重复调用同一工具

状态没记录已尝试路径，或工具返回没有可行的错误语义。

处理

事实指纹 + 行动去重 + 单工具重试上限 + 改变策略条件。

BAD ARGS
工具参数反复不合法

Schema 含糊，字段约束不足，或错误返回只有一段自然语言。

处理

结构化校验错误、示例、枚举、跨字段约束，必要时拆分工具。

SIDE EFFECT
重试导致重复写入

超时时无法区分“未执行”和“已执行但响应丢失”。

处理

幂等键、写前检查、执行回执、可补偿操作，高风险动作增加审批。

CONTEXT
上下文越长越糊涂

历史、证据和日志全量注入，关键约束反而被淹没。

处理

状态与消息分离；按阶段组装上下文；摘要可追溯到原始证据。

FALSE DONE
过早宣布完成

模型生成了看似合理的结果，但工具副作用或证据覆盖并未验证。

处理

完成条件写成可执行的 verifier，对最终结果和环境状态双重验证。
