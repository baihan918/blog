LlamaIndex 组件：一份文档如何变成 RAG 答案

Notebook 里的类很多，但主线只有一条：把外部资料变成可检索的知识，再让 LLM 基于证据回答。这个页面不按 import 顺序背 API，而是按数据的旅程来讲。

LlamaIndex 是编排层它连接 Reader、Embedding、向量库和 LLM，不是另一个大模型。
检索与生成是两步retrieve() 找材料；query() 再让 LLM 基于材料组织答案。
先看证据，再调 PromptRAG 效果差时，先检查解析、切块和召回，不要把问题都推给 LLM。

00 · THE WHOLE PIPELINE

点一下每个步骤，看清谁把数据交给谁

一个 RAG 系统不是 query_engine.query() 一行魔法。它前面有一条离线建库链，后面有一条在线问答链。

通俗类比：Reader 是收件员，Chunk 是切页编辑，Embedding 是给每段内容生成“语义坐标”，FAISS 是按坐标找相似材料的档案室，LLM 是最后根据材料写答案的编辑。
01 · DATA CONNECTORS

Reader 的任务：把五花八门的数据统一成 Document

PDF、Word、网页和数据库格式不同，后续的切块和索引不应该每次都适配一遍。LlamaIndex 用 Document 作为统一中间格式。

SimpleDirectoryReader

./data → List[Document]

扫描本地目录，按扩展名选择 Reader，适合入门和小型文件集。

PyMuPDFReader

PDF → 按页 Document

本地使用 PyMuPDF 提取 PDF 文字，快且不上传，复杂表格和扫描件能力有限。

BeautifulSoupWebReader

URL → HTML 文字

发起 HTTP 请求并去除 HTML 标签。它不是浏览器，不擅长必须运行 JavaScript 的页面。

LlamaParse

文档 → 云端结构化解析

更适合扫描件、表格、多栏排版。需要 API Key，文档会发往云端。

场景建议选择先确认什么
普通文字 PDFPyMuPDFReader提取后能看到正文，不是 %PDF 和交叉引用表。
扫描件 / 复杂表格LlamaParse 或 OCR数据是否可以上传，以及额度、延迟和成本。
普通静态网页BeautifulSoupWebReader是否混入导航、广告和页脚。
JS 渲染网页浏览器型 Loader源 HTML 里是否真的已经有正文。
查看本地 PDF + 网页混合加载
connectors.pyReader → Document
from llama_index.core import SimpleDirectoryReader
from llama_index.readers.file import PyMuPDFReader
from llama_index.readers.web import BeautifulSoupWebReader

local_docs = SimpleDirectoryReader(
    input_dir="./data",
    required_exts=[".pdf"],
    file_extractor={".pdf": PyMuPDFReader()},
).load_data()

web_docs = BeautifulSoupWebReader().load_data(
    urls=["https://example.com/article"]
)

documents = local_docs + web_docs
密钥不要写进 Notebook。源 Notebook 中的示例包含明文 LlamaCloud Key；这个页面已经完全移除。真实项目应从 LLAMA_CLOUD_API_KEY 环境变量读取，已暴露的 Key 应当更换。
02 · CHUNKING

Chunk 不是为了把文档切碎，而是让“每次召回”刚好能回答

块太大，一个向量混了多个主题；块太小，关键上下文又被切断。chunk_overlap 用少量重叠给切口上一份“保险”。

固定长度

简单、快，但可能在一句话或一张表中间切开。

结构切分

先尊重章节、段落、表格和页码，再在内部控制长度。

语义切分

在话题转换处切分，语义更完整，但成本和复杂度更高。

查看 SentenceSplitter 与 Node
split.pyDocument → TextNode
from llama_index.core.node_parser import SentenceSplitter

splitter = SentenceSplitter(
    chunk_size=1024,
    chunk_overlap=100,
    paragraph_separator="\n\n",
)

nodes = splitter.get_nodes_from_documents(documents)

# Node 不只有文字，还保留 source、file_name、页码等 metadata
for node in nodes[:3]:
    print(node.text, node.metadata)
03 · EMBEDDING

Embedding 是语义坐标：让“价格”和“售价”在空间里靠近

向量检索不是把文字原样存进 FAISS。它先用 Embedding 模型把文档块和用户问题都变成同一坐标系下的数组。

512 维BAAI/bge-small-zh

本地运行、中文友好、不需要 API 额度。

≠ 质量高低
1536 维text-embedding-3-small

OpenAI 托管、默认 1536 维，需要网络、Key 和可用额度。

维度高不等于一定更准。模型训练目标、语言和领域匹配度更重要。但 FAISS 的 d 必须严格等于 Embedding 输出维度。
建库和查询必须用同一个 Embedding 模型。换模型会换掉整个坐标系；已持久化的索引通常需要重建。
本地中文 Embeddingd = 512
from llama_index.core import Settings
from llama_index.embeddings.huggingface import HuggingFaceEmbedding

Settings.embed_model = HuggingFaceEmbedding(
    model_name="BAAI/bge-small-zh"
)
d = 512
OpenAI Embeddingd = 1536
from llama_index.core import Settings
from llama_index.embeddings.openai import OpenAIEmbedding

Settings.embed_model = OpenAIEmbedding(
    model="text-embedding-3-small"
)
d = 1536
04 · VECTOR STORE + STORAGE CONTEXT

FAISS 真的在存向量；StorageContext 负责把它接进 LlamaIndex

faiss.IndexFlatL2 是底层向量索引，FaissVectorStore 是适配器，StorageContext 则是把这套存储配置交给 VectorStoreIndex 的容器。

FAISSIndexFlatL2(d)真正保存和搜索向量
→
FaissVectorStoreLlamaIndex adapter把 FAISS 包装成统一接口
→
StorageContextvector_store=...把存储交给索引构建流程
vector_store=vector_store 怎么读？左边是 from_defaults 定义的参数名，右边是前面创建的 Python 变量。
查看 FAISS 索引组装
faiss_store.pynodes → vectors → FAISS
import faiss
from llama_index.core import StorageContext, VectorStoreIndex
from llama_index.vector_stores.faiss import FaissVectorStore

faiss_index = faiss.IndexFlatL2(d)
vector_store = FaissVectorStore(faiss_index=faiss_index)

storage_context = StorageContext.from_defaults(
    vector_store=vector_store
)

vector_index = VectorStoreIndex(
    nodes,
    storage_context=storage_context,
)
现在还只是进程内存。StorageContext 不等于已经落盘。要在程序重启后复用，需要明确调用 storage_context.persist(persist_dir="./storage") 并实现对应的加载流程。
05 · RETRIEVAL

retrieve() 是真正的检索步骤，也是 RAG 最好的调试窗口

先不让 LLM 写答案，直接看 top-k 找到了什么。如果证据都找错了，后面的 Prompt 再好也救不回来。

vector_retriever.retrieve("同仁堂安宫牛黄丸的市场价格")
#1
安宫牛黄丸终端价格段来源：同仁堂研报.pdf · 产品分析
score 0.91
#2
主力产品提价与需求风险来源：同仁堂研报.pdf · 风险提示
score 0.84
#3
同仁堂主要品种与渠道来源：同仁堂研报.pdf · 业务概览
score 0.79

retrieve()

只完成查询向量化和 top-k 召回，返回 List[NodeWithScore]，不生成中文答案。

适合：检查 score、正文、文件名和页码

query()

内部先调用 Retriever，再把找到的 Node 和问题交给 LLM 合成最终回答。

适合：给用户返回最终结果
查看 top-k 召回调试代码
debug_retrieval.py不调用 LLM
retrieved_nodes = vector_retriever.retrieve(
    "同仁堂安宫牛黄丸的市场价格"
)

for item in retrieved_nodes:
    print("分数：", item.score)
    print("来源：", item.node.metadata.get("file_name"))
    print("正文：", item.node.text)

06 · QUERY ENGINE + CHAT ENGINE

Query Engine 回答“这一问”，Chat Engine 还要记住“上一问”

查询引擎组合 Retriever 和 LLM；聊天引擎在这个基础上再加对话记忆。“你可以告诉我更多吗”只有结合上一轮才有明确含义。

Query Engine

适合单轮、独立问题。每次问题都应该信息完整。

例如：“世运电路 2023 年上半年营收是多少？”

Chat Engine

适合多轮追问。Memory 帮它理解代词、省略和对话主题。

例如：“它同比增长了多少？”
世运电路 2023 年上半年实现营业收入多少？
根据检索到的中报点评，营业收入为……
Memory 保留了“世运电路 / 2023 上半年 / 营收”这个上下文
那它同比增长了多少？
我会带着上一轮主题重新检索，而不是把“它”当成新对象。

07 · DATA AGENTS

Agent 不只回答：它先判断应该用哪个工具

Notebook 把“精确查某个问题”和“总结整篇文章”包装成两个 Tool。LLM 不必每次都走同一条路，而是根据意图选择。

LLM / Agent

理解用户意图，选工具，组装参数，整理工具返回值。

→
vector_query_tool

定点找与问题最相关的文档块。

summary_tool

遍历更多内容，对整篇文章做树形汇总。

“世运电路同比增长”

这是具体事实问题，更适合选择 vector_query_tool。

“总结一下兴证电子”

这是全局总结任务，更适合选择 summary_tool。

Agent 的核心不是“多调一次 LLM”。它的价值是动态选择能力；工具描述不清、参数契约不稳定，Agent 就容易选错。
08 · WHERE RAG BREAKS

RAG 不准不是一个问题，而是四个环节可能出问题

Notebook 最重要的收尾不是某个 API，而是教你判断错在哪一层。

01 查询理解

用户问“增长率”，系统只找回了两个绝对数，没意识到还要计算。

修复：意图分类 + 澄清 + 计算工具

02 数据解析

PDF 里的表格和图片没被识别，关键价格在建库前就已经丢了。

修复：更换 Reader / OCR + 建库前抽样验收

03 检索匹配

纯向量召回找到语义相似段落，但未必能满足精确关键词、时间和逻辑关系。

修复：分层切块 + metadata 过滤 + BM25 混合检索

04 答案生成

证据没有直接给结论，LLM 需要数值计算或多跳整合，容易臆测。

修复：工具调用 + 引用来源 + 答案校验
排查顺序：先打印 Reader 的正文 → 再看 Node 切分 → 再看 retrieve() 的 top-k → 最后才看 LLM 的回答。
09 · APPLICATION INTEGRATIONS

最后一层：把 Notebook 中的 query_engine 变成别人能用的服务

FastAPI / Flask 负责对外提供 HTTP API，Streamlit / Gradio 负责快速搭界面。这一层不应该每次请求都重新读 PDF、切块和建库。

1
离线建库文档解析、清洗、切块、Embedding 和入库按文档变更执行。
2
在线查询请求到来时只向量化问题、检索、组装上下文并调用 LLM。
3
可观测记录 query、召回节点、score、来源、耗时和最终答案，才能定位质量问题。
4
证据回溯向量行保留 source_path、页码、版本和时间，原始文件仍是事实来源。
查看最小 FastAPI 对外接口
api.pyGET /query
from fastapi import FastAPI

app = FastAPI()

@app.get("/query")
def query_llama(question: str):
    response = query_engine.query(question)
    return {"answer": str(response)}
10 · GLOSSARY

最后用一张术语表收口

Document
Reader 的统一输出，包含正文和文件级 metadata。
Node / TextNode
Document 切分后的小块，保留原文档关系和来源信息。
Embedding
把文字映射为固定维度向量，用于语义相似度计算。
VectorStoreIndex
负责将 Node 向量化、写入向量存储，并提供索引能力。
FAISS
本地高性能向量搜索库；当前 Demo 使用精确 L2 检索。
StorageContext
把 vector store、doc store 等存储能力组装给 LlamaIndex。
Retriever
根据问题召回 top-k Node，本身不生成答案。
Query Engine
将 Retriever 的证据交给 LLM，合成单轮最终答案。
Chat Engine
在查询引擎之上加入对话记忆，支持指代和追问。
Data Agent
让 LLM 根据用户意图选择检索、总结、计算等工具。
一句话总结：LlamaIndex 不是把一切藏进一个黑盒，而是把“读数据、切数据、存向量、找证据、写答案、选工具”这些环节组装成一条可替换、可调试的 RAG 流水线。
