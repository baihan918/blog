01 · ORIGINAL TEXT

图片原文

第一步不是立刻换模型，而是读懂上一步失败。工具应该返回结构化错误，至少包含错误码、错误类型、是否可重试、建议等待时间和可行的下一步。网络抖动、限流这类临时错误，可以在预算内按退避策略重试，并加入随机抖动避免同一时间集中重试。参数错误、权限不足和资源不存在需要换参数、请求用户授权或补充信息，继续原样重试没有意义。

第二步是换路。当前动作可以改变参数时，系统要说清楚上次为什么失败，并要求新动作和旧动作有实质差异。当前工具的能力边界不匹配时，换备选工具或降级到能完成部分目标的路径。一个工具在连续多个任务中都失败，调度层可以暂时打开熔断器，快速拒绝后续调用，避免每个 Agent 都在同一个故障上浪费预算。

第三步是 Replan。如果单个动作换了参数和工具仍无法推进，问题往往在原计划本身。系统从最近的检查点恢复，把原始目标、已完成结果、当前阻塞和已尝试路径交给 Planner，让它生成一份新的剩余计划。新计划应该有新版本，并把已证明无效的路径写入约束，否则 Replan 只是用更多 Token 再生成一遍旧计划。

多 Agent 的 Handoff 环节需要 Orchestrator 介入。它读取各 Agent 的职责、已访问路径和全局任务状态，决定是改派给有处置权的 Agent，还是暂停并请用户补充信息。Agent 的交接目标和接收条件也要写进路由规则，不能让两个角色随意把任务踢给对方。

02 · WHY AGENTS GET STUCK

Agent 为什么会原地打转？

本质上，是 Agent 没有获得足以改变下一次决策的新信息。相同目标、相同状态和相同策略，会让它再次选择相同动作。

?

错误信息不明确

工具只返回“执行失败”，没有错误类型、是否可重试和失败原因，Agent 不知道应该改变什么。

↻

执行结果没有写回状态

工具已经成功，系统却没有记录已完成步骤、新证据和外部副作用。下一轮模型仍认为任务没做，又重新执行一次。

≡

重试没有实质变化

提示词看似重新生成，实际使用的参数、工具和执行路径完全相同。

◎

目标与验收条件模糊

Agent 不知道什么算完成，只能不断搜索、分析、修改，再继续搜索。

×

计划前提已经失效

文件、权限、接口或数据已经不存在，Planner 却仍然按照旧计划向前推进。

⇄

多 Agent 路由成环

客服 Agent 要求风控批准，风控 Agent 又要求客服补资料；双方只有局部视角，也没有最终决策权，任务便来回交接。

v1

计划版本没有更新

工具结果已经证明原计划不可行，Planner 却没有生成新版本，Executor 只能继续执行已经过时的步骤。

典型的无进展循环
执行动作
  ↓
得到模糊失败
  ↓
状态没有更新
  ↓
Planner 仍认为旧计划有效
  ↓
再次选择相同动作
  ↺
判断标准：每次失败后，参数、工具、计划、已知状态或用户提供的信息，至少要有一项发生有效变化；否则就不是恢复，而是在重复。
no-progress detector · pseudo code
const repeated =
  current.tool === previous.tool &&
  current.argsHash === previous.argsHash &&
  current.errorCode === previous.errorCode &&
  current.progressScore <= previous.progressScore

if (repeated) {
  throw new NoProgressLoopError()
}
发现循环后：不要继续原样调用，应进入“换参数 → 换工具 → Replan → Handoff → 请求用户介入”的恢复路径。

04 · CLASSIFY FIRST

失败不是一种状态，而是一组不同问题

工具最好返回机器可读的错误码、错误类型、是否可重试、建议等待时间、调用标识和可能的下一步，而不是只丢出一句自然语言。

错误类型例子默认策略为什么
临时错误超时、连接中断、429、503退避 + 抖动 + 有限重试外部环境可能自行恢复
参数错误字段缺失、格式不符修正参数；必要时询问用户原样重试不会产生新结果
权限错误401、403、缺少授权请求授权或人工接管换模型通常无法补齐权限
资源错误文件、订单、工具不存在重新定位资源或 Replan原计划依赖已失效
能力不匹配工具不支持格式或动作换工具或降低目标需要真正不同的执行路径
语义失败调用成功，但结果不满足目标验证反馈 → ReplanHTTP 200 不代表任务成功

05 · THE MOST DANGEROUS GAP

先确认副作用，再谈重试

真实系统里最危险的情况不是“明确失败”，而是请求超时后，客户端以为失败，服务端其实已经完成。此时直接重试，可能重复扣款、重复下单或重复发消息。

!

不确定结果

网络在返回前断开，只能证明“没有收到响应”，不能证明“操作没有发生”。先用 operation_id 查询状态。

✓

幂等执行

给有副作用的动作附加 idempotency_key。同一业务意图重复提交时，服务端返回第一次结果，不再重复执行。

safe retry with idempotency
key = "send-report:report_123:user_456"

result = send_report(payload, idempotency_key=key)
if result.timeout:
    status = get_operation(result.operation_id)
    if status == "completed":
        return load_previous_result(key)
    if status == "not_started":
        return retry_with_same_key()
06 · RETRY WITH A BUDGET

重试是一种受控实验，不是循环祈祷

BACKOFF

等待时间指数增长，并尊重服务端 Retry-After。

1s → 2s → 4s
JITTER

加入随机偏移，避免大量任务同时醒来形成重试风暴。

± RANDOM
BUDGET

同时限制重试次数、总耗时、Token、工具调用次数和真实费用。

HARD LIMIT
CIRCUIT

同一工具或服务连续失败时，对该故障域熔断；不要轻易停止所有 Agent。

FAIL FAST
不要重试：确定性的参数错误、权限不足、已确认不存在的资源，以及会突破风险或费用边界的动作。
07 · CHANGE THE PATH

换路必须产生实质差异

“再试一次”不叫新策略。每次降级都要说明：上一条路径为什么失败、新路径改变了哪个约束、能力损失是什么。

⚙

改参数

缩小时间范围、减少批量大小、修正格式、降低并发度。适合调用边界不匹配。

⌁

换工具

主搜索不可用时切备用数据源；解析器不兼容时切换格式。适合能力或可用性故障。

◇

降级目标

无法完成全量分析时先返回已验证部分，并明确缺口。降级不能伪装成完整成功。

换模型的边界：模型输出不稳定、能力不足或上下文不适配时可以换；如果根因是工具故障、权限不足或数据缺失，换模型通常无效。
08 · REPLAN

不要用更多 Token 重写旧计划

Replan 的输入不是一句“刚才失败了”。Planner 必须看到可验证的当前状态，并把已经证明无效的路径写成硬约束。

⇥

交给 Planner 的状态

  • 原始目标与验收条件
  • 已完成结果及其证据
  • 当前阻塞和错误分类
  • 尝试过的路径与返回结果
  • 剩余预算、权限与时间
v2

新版计划的要求

  • 携带 plan_version
  • 复用有效结果，不从头再做
  • 避开已证伪路径
  • 给每一步写成功判定
  • 明确新的停止条件
09 · HANDOFF

交接不是把失败甩给另一个 Agent

多 Agent 场景可以由 Orchestrator 根据职责、权限和全局状态裁决；单 Agent 系统也能由工作流引擎或 supervisor 完成交接。重点是交接契约，而不是角色数量。

交接字段必须写什么避免什么
目标剩余目标、验收条件、优先级只说“你继续处理”
当前状态已完成结果、检查点、相关资源让接收方从头猜
失败证据错误类型、调用 ID、尝试次数只转发模糊报错
约束禁止路径、剩余预算、权限范围重复踩同一个故障
接收条件所需能力、权限与完成回执两个角色任意互相甩任务
10 · RECOVER FROM FACTS

没有检查点与日志，恢复只能靠猜

▣

检查点

保存 plan_version、step_id、输入摘要、已验证结果与外部 operation_id，从最近稳定点恢复。

◎

可观测性

串联 trace_id、tool_call_id、attempt、耗时、Token、成本和最终状态，才能定位失败发生在哪一层。

⏹

停止条件

成功、确定性失败、预算触顶、高风险动作或需要新授权时必须停止，并把控制权交还给用户。

11 · PRODUCTION FLOW

最终应落成这条恢复链路

这条链路保留原图的核心思想，同时把最容易造成生产事故的“副作用不确定”提到了重试之前。

记录失败结构化错误
副作用确认查询操作状态
有限重试退避 + 抖动
降级换路实质性改变
Replan从检查点恢复
Handoff契约式交接
人工接管权限 / 风险 / 预算
failure controller · pseudo code
async function recover(context, error) {
  const failure = classify(error)
  await saveCheckpoint(context, failure)

  if (failure.sideEffectState === "unknown") {
    const state = await queryOperation(failure.operationId)
    if (state === "completed") return reuseResult(state)
  }

  if (failure.retryable && context.retryBudget.hasRemaining()) {
    return retryWithBackoffAndJitter(context)
  }
  if (hasMeaningfulFallback(failure, context)) {
    return runFallback(context, failure)
  }
  if (!planStillValid(context, failure)) {
    return replanFromCheckpoint(context, failure)
  }
  if (canHandoff(context, failure)) return handoffWithContract(context)
  return requestHumanIntervention(context, failure)
}
