01 · Mental Model

把整个系统想成一家“研究型餐厅”

一个模型并不会因为“很聪明”就自动拥有公司文档、实时新闻和执行权限。真实系统要把不同职责拆开，再用一条工作流连接起来。

📦

解析器是验货员

把 PDF 包装拆开，识别文字、标题、表格和图片，尽量恢复成机器能理解的原材料。

🗂️

RAG 是资料管理员

收到问题后，从仓库里找最相关的几份材料。它负责“找”，不负责决定整个任务怎么做。

🧑‍🍳

Agent 是值班经理

理解顾客需求，决定查内部菜单还是外部市场，安排动作，最后组织成完整答复。

📚

另一个更准确的类比：修复古书

PDF 不是干净的字符串，而像一本装订复杂的书。普通提取器只“抄下看见的字”；智能解析器还要判断先读左栏还是右栏、哪些格子属于同一张表、公式上下标是什么。解析完成后，切块才像把书编成一张张索引卡。

03 · Document Parsing

文档解析到底在“解析”什么？

同一页 PDF，在人眼里是一篇文章；在程序眼里可能只是一堆散落在坐标系中的字符、线条和图片。

第 1 层：文字

识别“ES9”“150 kWh”等字符；扫描件还需要 OCR。

TEXT / OCR
第 2 层：版面

判断标题、正文、页眉页脚、左右栏，以及正确阅读顺序。

LAYOUT
第 3 层：结构

恢复表格行列、列表层级、图片标题、公式与章节关系。

STRUCTURE
第 4 层：语义

根据业务需要输出 Markdown、JSON 或字段对象，供切块与检索使用。

SEMANTICS

普通文本 PDF

如果文件自带干净文本层，PyMuPDF、pdfplumber 往往更快、更便宜，也更容易私有化。

复杂或扫描 PDF

多栏、扫描、复杂表格、公式和图文混排需要 OCR、布局识别或多模态模型，才是 LlamaParse、DeepDoc、MinerU 的主场。

Notebook：把 .pdf 路由给 LlamaParseReader Adapter
parser = LlamaParse(
    api_key=os.environ["LLAMA_CLOUD_API_KEY"],
    result_type="markdown",
    language="ch_sim",
)

file_extractor = {".pdf": parser}
documents = SimpleDirectoryReader(
    "./data", file_extractor=file_extractor
).load_data()
边界：SimpleDirectoryReader 是文件发现和解析器调度层；LlamaParse 才是真正处理 PDF 的服务；返回的 Document 是 LlamaIndex 对结果的统一封装。
04 · Parser Choice

LlamaParse、DeepDoc、MinerU 怎么选

先看产品形态，再谈准确率。没有脱离文档样本的“绝对最好”，同一个工具在合同、论文、发票和扫描手册上的表现可能完全不同。

CLOUD SERVICE

LlamaParse

像“把文件交给外部专业翻译社”：几行 API 就能得到结构化结果，运维最少，但有费用、网络和数据出域问题。

05 · Retrieval

项目里其实有两套 RAG

两条链路解决的是不同的新鲜度问题：内部产品手册稳定且可信，市场信息实时变化，需要联网补充。

本地 RAG：查 ES9 产品手册

  • 58 个约 300 字的 chunk
  • BGE-M3 同时生成 dense 与 sparse 向量
  • Milvus Lite 保存两类向量
  • WeightedRanker：dense 1.0、sparse 0.7
  • GPT-4o 根据前 10 条片段生成局部答案

联网 RAG：查竞品和实时信息

  • Serper 查询 Google 搜索结果
  • 多个线程并行抓取网页正文
  • 按 1000 字切块
  • MiniLM + Chroma 返回前 20 条
  • GPT-4o 生成带引用的联网回答
🔎

Dense + Sparse 像“按意思找”再加“按原词找”

用户问“以人为本的座舱”，dense 检索能找到“舒适、人体工程学、沉浸体验”等语义接近内容；sparse 检索擅长命中“座舱”“ES9”等明确词。混合检索把两种证据合并，减少只懂意思却漏掉专有名词的问题。

别忽略证据边界：项目的 Prompt 允许“没有相关内容时按自己的知识回答”，这会让带引用的 RAG 回答混入无引用知识。严肃业务应明确区分“证据支持”“模型推测”和“没有答案”。
06 · Agent Workflow

Agent 是怎么决定调用哪个工具的？

项目让 Qwen Plus 输出 JSON 计划，再由 Python 展平动作并通过中文工具名分发。这是一种合理的教学骨架，但不是标准 Function Calling。

试试项目的路由规则

本项目：手写 JSON 路由

  1. 模型输出普通 JSON 文本
  2. json.loads() 解析计划
  3. Python 根据 action_name 调函数
  4. 结果加入普通列表 memory_global
  5. 再次请求模型生成最终答案

标准 Function Calling

  1. 应用把工具 Schema 放进 tools
  2. 模型返回结构化 tool_calls
  3. 应用执行对应函数
  4. 追加匹配 tool_call_id 的 role=tool 消息
  5. 再次调用模型获得最终回答
“3 个 Agent”更准确的说法：这是三个角色阶段——Planner、Action/Executor、Answer。Action 本身主要是确定性的 Python 调度，并不是另一个会自主推理的智能体。
07 · Reality Check

从教学 Demo 到可靠工程，还差什么

读代码不能只看“它想表达什么”，还要看从干净环境重启后是否真的按这个流程运行。

安全

API Key 被直接写进 Notebook

密钥应立即轮换，并统一改为环境变量或密钥管理服务。Notebook 输出、检查点和分享文件也要做 secret scan。

逻辑

第一条执行结果被丢弃

memory_global.extend(memory_new[1:]) 会跳过第一条结果，更合理的是保留全部结果，或显式说明为什么过滤。

逻辑

反思阶段重复执行旧 actions

reflection() 生成了新动作，但代码再次调用 process_actions(actions)，没有真正消费反思结果。

状态

Notebook 依赖隐藏的 Kernel 状态

agent_plan() 引用了源码中未定义的 memory；历史输出还出现同步函数被当作 coroutine 的警告。应执行 Restart & Run All 验证。

工程

README、文件名和依赖清单不一致

README 安装 requirements.txt，实际是 requirement.txt，而且没有列全 Milvus、MinerU/BGE、Chroma、LlamaParse 等依赖。

质量

异常被静默吞掉，引用也没有验证

工具失败后只继续下一轮，会让最终模型在缺失证据时自信回答。生产系统应该保留错误类型、重试状态和来源可追溯信息。

08 · Production Shape

真实项目推荐做成可替换流水线

成熟方案不是“所有 PDF 固定走某个最强解析器”，而是先识别复杂度，再路由、缓存、评测和降级。

① 文件识别格式、扫描件、页数、语言、敏感级别
② 解析路由PyMuPDF / MinerU / DeepDoc / 云服务
③ 统一结构文本、标题、表格、图片、页码、坐标
④ 质量闸门空页率、乱码率、表格和阅读顺序抽检
⑤ 切块入库按章节和语义切块，Embedding 后持久化
生产思路：路由 + 缓存 + 降级pseudo_python.py
def parse_document(file, policy):
    cached = cache.get(file.sha256, parser_version)
    if cached:
        return cached

    if policy.must_stay_private:
        parser = mineru if file.is_complex else pymupdf
    elif file.is_complex:
        parser = llama_parse
    else:
        parser = pymupdf

    result = parser.parse(file)
    quality.assert_acceptable(result)
    cache.save(file.sha256, parser_version, result)
    return result
评测方法：拿 30～100 份真实业务文件建立黄金样本，分别统计标题层级、阅读顺序、表格、公式、页码坐标、耗时和成本。不要只看厂商演示文件。
09 · Check Yourself

用 4 道题检查是否真的理解

最小术语表

Parser
把文件恢复为文本、布局和结构数据的组件，不负责检索答案。
OCR
从页面图片识别字符；有文本层的 PDF 不一定需要 OCR。
Chunk
为了检索而构造的知识单元。解析结果可以再次按章节和语义切块。
Dense Retrieval
用向量语义相似度找内容，擅长“意思相近但用词不同”。
Sparse Retrieval
根据词项权重匹配内容，擅长专有名词、型号和精确关键词。
Hybrid Search
融合 dense 与 sparse 结果，兼顾语义理解和关键词命中。
Planner
把用户目标拆成动作计划；计划仍需应用程序校验与执行。
Memory
项目中只是存工具结果的 Python 列表，不等于长期记忆系统。
一句话总结：这个项目先把产品 PDF 解析并做成可检索知识库，再让规划模型决定查本地还是查网络，Python 执行工具，最后由回答模型整合证据。理解每个边界，比记住某个框架 API 更重要。
